# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read these first

Two documents define the product and must be read before non-trivial work:

1. **`PRODUCT.md`** — the product vision (the "what" and "why"). Decided. Don't re-litigate.
2. **`SERVER.md`** — the server spec (the "how"). The architectural frame and the full sync/sharing/realtime contract; endpoint-level design for unbuilt domains is still planned interactively.

If a code decision contradicts either document, the document wins. `PRODUCT.md` wins over `SERVER.md` on conflict. But the specs are a moving snapshot of the owner's direction, not law — when his live direction differs, follow him and update the docs rather than citing old text back.

## No shortcuts

**Nothing in this app is “fine how it is.”** Only the user may say “fine for
now” — and when he does he means *we will get to it in a patch or two*, which is
his call to defer, not permission to stop looking. An agent never says it.

- Describe what is actually there, then **name the real version** — what it would
  be if it were built properly — and offer to build that.
- Size is information, not a verdict. “That needs a migration and a deploy” is
  useful. “That’s overkill at your scale” is deciding for him.
- **Don’t take the shortcut in the code either.** No regex standing in for a data
  model, no poll standing in for a push, no field reused for a thing it doesn’t
  mean. If the proper route is long, say it is long and start on it.

This rule was bought: invites were shipped as a `bombers://room/<id>` string
regex‘d out of DM text — no state, no expiry, forgeable — and then called fine.

## Current state (what's built vs. spec)

The repo is **no longer spec-only** — a working HTTP API is in place. The doc above (`SERVER.md`) still describes the full target including unbuilt domains; this section is the source of truth for what actually exists today.

**Built (`internal/`):**

- `config/` — twelve-factor env loading (`config.Load`). Vars: `HOST` (bind interface; empty = all), `PORT` (default 8080), `TOKEN_SECRET` (required), `DB_BACKEND` (`external` default, or `embedded`) with `DATABASE_URL` (required only for `external`), `AUTO_MIGRATE` (opt-in; see `migrate/`), `CORS_ALLOWED_ORIGIN` (comma-separated; default `http://localhost:1420`, the Vite dev origin — `main.go` always adds the packaged client's `http://tauri.localhost` on top; the `AllowedMethods` beside it must list every verb any route is registered with — a route whose verb is missing there works from curl and fails its preflight in the packaged client, so a route with a new verb adds it there), `ADMIN_USERNAME` (optional — promotes that account to admin at boot; an unknown name warns rather than failing startup), and media: `MEDIA_BACKEND` (`s3` default, or `fs`) + `MEDIA_DIR` (the `fs` root), then the S3 block — `S3_ACCESS_KEY`/`S3_SECRET_KEY` (required only for `s3`), `S3_ENDPOINT` (default `localhost:9000`), `S3_BUCKET` (default `bombers-media`), `S3_USE_SSL` (default false), and `ICE_STUN_URLS` (comma-separated `stun:`/`stuns:` URLs for `GET /ice`; empty = the two public Google STUN servers; parsed by `config.Load` itself via `transfers.ParseSTUN`, so a bad value — a `turn:` entry above all — stops the server before the database or anything else starts, with an error naming the variable and the entry; `Config.ICEStunURLs` is the parsed, never-empty list). **`Load` is the one place the environment is checked, and it runs first thing in boot** — before Postgres, a pool or the media store is touched — so a bad variable stops the server there with an error that names the variable and the value it was given. It validates the enumerations (`DB_BACKEND`, `MEDIA_BACKEND`, `SIGNUP_MODE`: exact match, case included, never corrected to a neighbour), the `PORT` and the shape of `S3_ENDPOINT` (shape only, and only for the `s3` backend — whether anything answers there is learned over the network, and a server that refuses to boot because the object store was briefly down is worse than one that finds out on first use), and `ICE_STUN_URLS` (via `transfers.ParseSTUN`). **It collects every problem and returns them together on one line** rather than stopping at the first, so fixing an install is one pass, not one restart per typo; and a problem is never reported against the wrong variable (an invalid `DB_BACKEND` does not also demand a `DATABASE_URL` it would have needed). `doctor`, `backup`, `update` and the console all call it, so all of this is a hard failure for each of them. **`config.SignupRequiresAllowlist(mode)` fails closed, and the comparison must stay the way round it is:** it asks whether the mode is EXACTLY `open`, so anything else — a typo, another case, empty — keeps the allowlist in force. `SIGNUP_MODE` is read again on every sign-in by `settings/`, so a bad value cannot rely on having been refused at boot; comparing against `list` instead would make every value that is not `list` mean "no allowlist", and a typo would open the door. `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET`/`DISCORD_REDIRECT_URL`, `WEBSITE_URL` and `SIGNUP_MODE` are loaded into `Config` too, but nothing reads those fields — `settings/` resolves the same variables itself, per request. `main.go` loads `.env` first, and `setup/` then fills anything still unset from `config.json`.
- `store/` — `pgxpool` connection (`store.NewPool`), pings on startup.
- `httpx/` — shared JSON response/error helpers (`WriteJSON`, `WriteError`). All handlers use these.
- `logx/` — the shared **leveled, colored logger** (stdlib only; a leaf every package imports, so no cycles). One line per call: `[<timestamp>][<LEVEL>]: <message>` at `INFO`/`WARN`/`ERROR`/`FATAL` (`Fatal` exits 1); the level label is width-padded so the `:` aligns. 24-bit truecolor auto-enables **only** when stdout is a character device and `NO_COLOR` is unset (piped/redirected output is plain and greppable, and the launch banner is skipped). `LOG_TIME_FORMAT` (`time`|`datetime`|`iso`, default `datetime`) sets the timestamp layout at boot; the console's `logtime` command switches it live (guarded by an `RWMutex`). `Init()` runs once in `main` right after the `.env` load. Every domain's request-error logs and `main`'s startup/lifecycle lines route through this — no package imports `log` anymore.
- `types/` — shared domain types (e.g. `User`) used across packages.
- `auth/` — the JWT issuer (`token.go`: stateless HS256 access tokens, DB-tracked rotating refresh tokens with `jti`), `Service` (rotation/reuse detection), `RequireAuth` middleware, and request-context helpers. Owns all signing — other domains depend on it, never duplicate claim shapes. Access TTL 15m, refresh TTL 30d.
- `users/` — Discord sign-in (`discord_handler.go`: start/callback/claim/signup), `/me`, friend-code generation, username normalization/validation.
- `discord/` — the **Discord OAuth2 client**; Discord is **the only way in** (no password routes are registered). A leaf (`discord.go`: net/http + JSON, no DB, no domain imports) that answers one question, who this is on Discord: `AuthorizeURL`/`Exchange`/`Me`/`Connections`/`Revoke` against the version-pinned `v10` API, asking for **`identify` + `connections` and nothing more** (a test pins it; no email, which would only be a liability). **No Discord token is ever stored**: the callback exchanges the code, reads the identity and connections, then revokes the token, so a stolen database holds no keys to anyone's Discord — the price is that the handle, avatar hash and connections (`users.discord_*`, stored but not yet served by any endpoint) refresh only at sign-in. The flow is `users/discord_handler.go`, which builds a **fresh client from `settings/` on every request**, so a console change applies to the very next sign-in. The app's `start` sends a **port, not a URL** (the return is always `127.0.0.1:<port>`, so there's no open redirect), and the **callback never returns tokens**: it redirects with a single-use **handoff code** the client trades at `POST /auth/discord/claim`, which keeps tokens out of URLs and browser history. OAuth state, signup tickets and handoffs are in-memory, short-lived and single-use (`discord_pending.go`). Gatekeeping: a **blocked** identity (`signin_attempts.blocked_at`) is refused before anything else, and a failed check counts as blocked; an existing account signs in unless banned; an identity with **no account** is recorded in `signin_attempts` and, from the **app**, refused with a bare `not_authorized` — the installer is only reachable after signing up on the website, so that client didn't come the one way there is. From the **website**, `signup.mode=list` also requires the id on `signup_allowlist` (migration `discord_auth`), then `POST /auth/discord/signup` creates the account under a username the person picks. Who gets in is managed only at the console (`allow`/`unallow`/`allowed`, `attempts`, `block`/`unblock`, `link`/`unlink`); no HTTP route widens access.
- `friends/` — friend graph: codes, requests (send/accept/reject), list, remove, block/unblock.
- `profiles/` — both profile cards. **Self-card** (`profiles` table, `handler.go`/`store.go`): a user's own published profile (display name, birthday, country, timezone, city, nickname + visibility `friends`/`private`); **age derived from birthday at read time, never stored**. **The birthday is TEXT, not a DATE** (`birthday_without_year`): as much of the date as the user knows — `YYYY-MM-DD`, `MM-DD`, `YYYY-MM`, `YYYY` or `MM`, exact and zero-padded, year 0001–9999, and a day has to exist in its month (`02-29` passes without a year, `2023-02-29` doesn't). It goes back out exactly as stored and `age` comes only from a whole date, null for every partial one; `""` clears it (NULL) and anything else is `400 invalid_birthday`. `GET|PUT /me/profile`, `GET /profiles/{userID}` (gated by accepted friendship + visibility → opaque `404 profile_not_found`). Profile responses expose `avatar_url`/`banner_url` (null until uploaded) via a narrow read of `media/`'s `user_media` table + the shared `types.MediaURL` shape. They also ALWAYS carry `avatar_crop`/`banner_crop` — `{x, y, scale}`, the framing the owner chose (x/y are CSS object-position percentages 0–100, scale is zoom 1–4) — from six REAL `profiles` columns defaulting to 50/50/1, so a card with nothing stored still comes back centred and never at scale 0. On `PUT /me/profile` both are OPTIONAL and **omitted means kept**: a NULL argument COALESCEs against the existing row, never `EXCLUDED` (which holds the insert's fallback and would reset the framing on every partial save — the client's first-run setup sends a partial draft); out of range is `400 invalid_crop`. A save nudges every accepted friend with a `profile` frame carrying `{"from": <owner id>}`. **About-card** (`about_cards` table, `about_handler.go`/`about_store.go`): the private notes user A keeps *about* user B. The rich field set is stored as an **opaque JSONB `content` blob** (server never inspects it; client owns the shape) + a `visibility` of `private` (author only, default) or `subject` (the person it's about may read it too). `GET /me/about` (list mine, for restore), `GET|PUT|DELETE /me/about/{subjectID}` (PUT gated on accepted friendship → opaque `404 subject_not_friend`), `GET /about/{authorID}` (what a friend shared about me → opaque `404 about_not_found`). The domain owns a narrow `areFriends` query against the `friendships` table rather than importing `friends` (same loose-coupling tradeoff the domains already make). **Facts only.** Birthday/age, country, timezone, city and nickname are the same for everyone you're linked to, so they are plain columns any accepted friend reads; `GET /profiles/{userID}` does NO per-viewer redaction. **Notes are not shared**: the per-viewer published card (`PUT /me/card`, `GET /cards/{ownerID}`, table `published_cards`) was removed 2026-09-14 along with note sharing in the client (migration `drop_published_cards`), as its predecessor `profile_shares` was before it. **There is no bio**: the freeform `bio` column was dropped the same day (`drop_profile_bio`); a client that still sends one has it ignored.
- `presence/` — **who's around** (`presence.go`/`handler.go`, table `presence`): one row per user holding the status they CHOSE and when they were last HEARD FROM. Neither is the answer alone — a stored `online` from a laptop that shut three days ago is a lie, and a fresh heartbeat from somebody who set themselves offline is none of your business — so `Effective` computes what a friend actually sees at read time and never stores it (the same rule profiles follows for age). `offline` is honoured exactly (invisible AND disconnected, so a heartbeat can't override it); everything else expires after `StaleAfter` (3 min, against the client's 60s beat — generous on purpose, because a presence dot that flickers is one nobody reads). `PUT /me/presence` is the status AND the heartbeat in one write, because two calls that must agree are two calls that can disagree; `GET /presence` answers for every accepted friend at once, with never-seen friends coming back `offline` rather than missing. Friends only — there is no way to ask about a stranger, matching the no-username-search rule. **No history**: the table only ever answers "now", since a log of when somebody was at their computer is a surveillance feature wearing an analytics hat. Owns the same narrow `areFriends`-style join the other domains do.
- `sync/` — **publish/pull**, the heart of client↔server (`SERVER.md` §Sync). The server is a **versioned key-value store of published items** keyed by the client's ULID, scoped to an account; it never edits content. `published_items` table keyed by `(owner_id, id)`, with `content` (opaque JSONB), client `updated_at` (authoritative for **last-write-wins**), a `deleted` tombstone (so deletes propagate), and `server_updated_at` (drives incremental pulls). `POST /sync/push` upserts a batch in one transaction, LWW by `updated_at`, returning each item as `applied` (server took it) or `stale` (server kept a newer copy → client should pull). `GET /sync/pull[?since=<RFC3339>]` returns the caller's items (full, or only those server-written since the cursor), tombstones included. `GET /sync/status` returns `last_synced_at` + live item count (a `sync_state` row bumped on each push). **Triggered, not streamed** — real-time nudges that make pull "feel live" are the later `realtime/` WebSocket layer; pulling items others shared with me is the later `sharing/` domain (today pull is own-items only). NB: the package is named `sync` (shadows stdlib `sync` within its files — it needs neither).
- `nodes/` — the **official node store** (`handler.go`/`store.go`, table `nodes`): this server's OPERATOR-published nodes in the SDK **`{manifest, files}`** format (the same opaque-JSONB bundle shape `nodeshare` carries; 4 MiB cap). The table denormalizes `id`/`name`/`version` out of the manifest for cheap listings. `GET /nodes` (catalog — id/name/version + icon/description/tags pulled from each manifest, never the files), `GET /nodes/{id}/bundle` (the full `{manifest, files}` JSON for install; **the id is PathUnescaped** — a node id carries a namespace and therefore a colon (`core:weather`), a client percent-encodes it, and chi hands back the raw segment, so every lookup missed while the catalogue looked fine; the `/bundle` suffix keeps it clear of nodeshare's static `/nodes/received`; unknown id → `404 node_not_found`). Publishing is **operator-only**, two ways into the same operation: the console (`publish <path>` / `unpublish <id>` / `store`), or the **admin-gated** `POST /nodes` + `DELETE /nodes/{id}` — the HTTP path exists so an operator can publish from the CLIENT (`publish <project>` in its terminal) instead of copying a bundle onto the server box. A self-hosted server's operator curates their own store the same way (isolated per server). The old any-user `POST /nodes` + single-file `node.js` bytea format were removed by the `20260706130000` migration (drop + recreate; nothing was published in the old format).
- `apitokens/` — **long-lived, scoped, revocable credentials** (`scope.go`/`store.go`/`middleware.go`/`handler.go`, table `api_tokens`): how something that ISN'T a person talks to a server — a script, a mini-client, an agent. The session model in `auth` is built for a human at a client (15m access token, single-use rotating refresh); nothing there can be handed out narrowly or taken back. A token is `bmb_` + 32 random bytes, shown ONCE and stored only as a SHA-256 hash, so the server can check one and can never show one again. `Resolve` checks revocation and expiry **in the query** (a condition applied in Go is one somebody can forget) and stamps `last_used_at` in the same round trip. Scopes are deliberately few and coarse — `store:read|write`, `notes:read|write`, `friends:read`, `people:read`, `messages:read|write`, plus an implicit `profile:read` — because a long fine-grained list reads as careful and behaves as careless. `RequireScope` gates a route: a SESSION passes unscoped (it IS its owner), a TOKEN must hold the scope, and a miss is `403 insufficient_scope`, never 401. **A scope is a ceiling, not a grant** — `store:write` doesn't make a token an admin. `auth.RequireAuth` accepts either credential on the same header, branching on the prefix, via a `TokenResolver` seam wired in `main` so the dependency points one way (apitokens → auth); `auth.APITokenPrefix` is a duplicated constant a test pins to `apitokens.Prefix`. `GET|POST /me/tokens` + `DELETE /me/tokens/{id}` are **SessionOnly** — a token that could mint or revoke a token is privilege that extends itself, so there is no scope for it. `GET /token-scopes` is unauthenticated (a consent screen needs it before a token exists).
- `admin/` — the operator **ROLE** (`users.is_admin`) and the HTTP gate admin-only routes hang off (`RequireAdmin`, which runs after `RequireAuth`; non-admin → `403 forbidden`, and a DB failure fails CLOSED). Before this, "operator" meant "whoever holds the console" — privilege by physical access, which made every operator action unreachable from the client. Granting is deliberately console-or-config only (`admin <user>` at the prompt, or `ADMIN_USERNAME` at boot): there is no endpoint that grants admin, because an HTTP path to self-promotion is precisely what you don't want. Today it gates publishing to all four stores (nodes, games, packs, releases); the rest of the console surface can ride the same gate later.
- `settings/` — **configuration an operator changes at runtime** (`settings.go`, key/value table `settings`), as opposed to what a deployment decides. A port, a database URL or where media lives belong in env; which Discord application signs people in and who may sign up have to change without editing a file and restarting, and a wizard-configured install has no env file to edit, since `config.json` only carries what the wizard asks. The keys are a **closed set** (`Known`; anything else is `ErrUnknownKey`, so a typo never becomes a row nothing reads): `discord.client_id`, `discord.client_secret` (masked in listings), `discord.redirect_url`, `website.url` and `signup.mode` (`list`, the default, or `open`). `Resolve` answers **env → table → default** and reports which source won. **The environment still wins** (each `Setting` names its variable, e.g. `DISCORD_CLIENT_ID`, `SIGNUP_MODE`), so a container deploy behaves as it did and an operator who can't reach the console can override from outside. A DB error resolves to the default rather than failing a sign-in, because every default is the safe answer (nobody can sign in, signups closed); `Set` with no value deletes the row instead of storing `""`. `users.DiscordHandler` reads it **per request**, so a change is live on the next sign-in with no restart, and `main.go` only logs at boot whether sign-in is configured. It's written only at the console: `config` (every value and where it came from), `set <key> [value]`, `discord [set <id> <secret> <redirect> | clear]` (all three at once, since two of three configured is the same as none) and `signups [list|open]`. Each command **says when an env var is overriding** what it just saved, instead of appearing to work. There is no HTTP route for any of it.
- `console/` — the **interactive admin console** (Minecraft-style `bombers>` prompt on stdin). A bare `bombers` (or `bombers console`) opens it as its own process against the same database; `bombers start --foreground` runs it inside the server unless `--headless`. Either way it's a small command registry + loop — `help`, `users` (username/id/created), `status` (uptime, address, DB + media health), `logtime` (show/switch the live log timestamp format), the **node-store publish surface** (`publish <path>` — read + validate a `{manifest, files}` JSON file and upsert it into the store; `unpublish <id>`; `store` — list published nodes; see `examples/sample-store-node.json`), and `stop` (aliases `quit`/`exit`) → graceful `http.Server.Shutdown` in the in-process console, while the standalone one just leaves and the server keeps running. Local-operator-privileged by definition (whoever holds the terminal — no auth); the store commands are the deliberate step past read-only (the admin-gated HTTP routes are the other way to publish). **User administration** is here too: `ban <user> [reason]` / `unban` / `banned` (list) and `deluser` — resolving a user by username OR id. A ban is a mark (`users.banned_at` + `ban_reason`), not a deletion, so it's reversible and the user's content stays consistent for everyone else; it's enforced at the DOORS (login refuses, refresh refuses + their refresh tokens are cleared) rather than on every request, so it takes hold within one 15m access-token lifetime without adding a DB read to every authed call. `deluser` is irreversible — every cross-user table cascades — so it makes you type the username back, and REFUSES outright when stdin isn't interactive. **The typing is not on the clock:** a command's context (`commandTimeout`, 5s) starts before the command runs, so a prompt inside it spent the operator's time and a slow confirmation expired the delete. `Console.confirm` now returns the context for the work that follows, started AFTER the answer, and `deluser` runs its picture read and its delete under that and never under its own `ctx` again (a test pins it as text, since it cannot run without a database). `confirm` is the only prompt inside a console command; `bombers restore` has its own and runs under no timeout. The console is also the ROOT OF TRUST for the admin role (`internal/admin`): `admin <user>` grants it, `unadmin` revokes, `admins` lists. There is deliberately NO endpoint that grants admin — the only ways in are at the machine or via `ADMIN_USERNAME` at boot. A non-TTY stdin or console EOF falls back to headless signal-waiting (never spins). `main.go` serves via `http.Server` in a goroutine and shuts down gracefully in every mode. On launch `cmd/bombers` prints a colored **BOMBERS/NOTEBOOK** ASCII banner (TTY only, via `banner.go`) before the prompt; the old plaintext console intro line is gone — the banner plus a `console ready` INFO log replace it. The sign-in commands (`config`, `set`, `discord`, `signups`, `allow`/`unallow`/`allowed`, `attempts`, `block`/`unblock`, `link`/`unlink`) are covered under `settings/` and `discord/`.
- `setup/` — the **config file under the environment, and the setup wizard** (`setup.go`, `wizard_tui.go`; no internal imports). `DataDir` resolves `BOMBERS_DATA_DIR` or `<user config dir>/Bombers` (`~/.config/Bombers` on Linux) **without creating it** — only `Save` does, so a pure-env host leaves nothing on disk. The same directory holds `install.json`, `server.pid`/`server.log`, `pg/` and, by default, `media/`. `FileConfig` is `<dataDir>/config.json` (0600, because it holds `TOKEN_SECRET`), and **`Apply` sets each field only where the environment left it unset**, so a real env var always wins and `config.Load` stays a plain env loader. `EnsureSecret` mints a random `TOKEN_SECRET` when neither side has one, and `start`/`setup` save it so tokens survive restarts. `buildAndServe` layers the file on **every start** (a no-op when env is complete). If `NeedsWizard` says config is incomplete (`DATABASE_URL` counts only for the external backend, S3 keys only for S3 media), it runs the wizard when stdin is a terminal and otherwise refuses with "run `bombers setup`". `bombers setup` always runs the wizard, then saves and migrates. There are four questions. **Where it lives**: LAN binds `0.0.0.0`; a **domain** binds `127.0.0.1` behind Caddy, because the server deliberately doesn't terminate TLS (certificates need ports 80/443, and those need root), so setup prints a Caddyfile instead. Then **port** (1024 or above, for the same reason), **database** (embedded by default, or a URL) and **media** (files under `<dataDir>/media` by default, or S3). Two front ends — `huh` selects at a terminal, typed prompts on a pipe — feed the same `apply*` functions, because a wizard only a human can drive can't be tested or scripted. Ctrl+C in the wizard saves nothing — from `bombers setup` or a `start --foreground` that asked — since a half-answered config looks finished. `doctor`, `console`, `update` and `backup`/`restore` layer the file the same way.
- `embeddedpg/` — **Postgres as a supervised child process** (`embeddedpg.go`, via `fergusstrange/embedded-postgres`) for `DB_BACKEND=embedded`: no Docker, no system install. **Postgres 16 is pinned** so the on-disk data format can't shift under a server upgrade. The first start downloads the binary (checksum-verified) into `<dataDir>/pg/cache` and every later start boots offline, with the cluster in `pg/data`. It binds **loopback only** (`listen_addresses=localhost`, set explicitly so a library default can't widen it) on port **5433** rather than 5432, so it can't collide with a system or docker-compose Postgres, using fixed `bombers` credentials that never leave the machine. `ConnString()` is the one source of that URL for the server, `bombers console` and backup. A 32-bit build is refused up front with a rebuild hint, since there's no 386 Postgres upstream (`doctor` and the wizard say so too). `stopStalePostgres` clears an orphan left by an unclean shutdown, but only when the port is actually held and only the pid in its own `postmaster.pid`; `InUse()` exists so `update` can **refuse** instead, because a listener on 5433 may be a running server's live database. Only Postgres's WARNING/ERROR/FATAL/PANIC lines reach `logx`. `buildAndServe` starts it and **migrates before opening the pool**, and `shutdown` closes the pool before stopping Postgres so no query races the stop. `migrateNow` (for setup/update) starts it, migrates and stops it again, since nothing is listening between runs. Postgres won't run as root, which is why `svc/` refuses to install a root-run service.
- `migrate/` — **applies the embedded migrations through the goose library** (`migrate.go`), so nothing ever needs the goose CLI or a `-dir` flag. `migrations/embed.go` embeds `*.sql`, and goose runs over `database/sql` (pgx's stdlib driver) against the same `goose_db_version` table the CLI uses, so the two stay interchangeable (the CLI is still there for `down`/`status`/`create`). goose's own logging is silenced in favour of one `logx` summary line. `Up` reads the embed. **`UpFrom(dir)` reads a checkout's `migrations/` directory** instead, for `update`: that command is by definition the OLD binary with a stale embed, but it has just rebuilt from that checkout, so the newest files are sitting on disk. This replaced exec'ing the new binary with a hidden argument — a private command that could never be renamed, because the old binary is the one choosing what to call. `goose.SetBaseFS` is global, so a directory run must reset it to `nil`, and `migrate_test.go` pins that the directory and the embed hold the same versions. `Version` reports where the schema landed. Callers: `buildAndServe` (always for embedded Postgres; for an external database only with `AUTO_MIGRATE=true`, opt-in so a schema change is never a side effect of a restart) and `migrateNow` in `cmd/bombers`, used by `bombers setup` (the embed) and `bombers update` (the checkout). There is no `migrate` subcommand.
- `backup/` — **one portable file** (`backup.go`; the `bombers backup [file]` and `bombers restore <file>` commands are in `cmd/bombers/backup.go`): a `.tar.gz` holding `database.sql`, every media object as a plain file under `media/`, and a `manifest.json`. **Portable, not a snapshot**: it restores into whatever the target is configured with (embedded or external Postgres, filesystem or S3 media), because a backup that only restores onto an identical setup can't outlive the machine. The database half **shells out to `pg_dump`** (`--clean --if-exists --no-owner --no-privileges`, so restoring over a live database is the same as restoring onto an empty one) and to `psql` with `ON_ERROR_STOP=1`, rather than serialising rows: a hand-rolled dumper that gets one escaping rule wrong makes an archive that looks fine and restores wrong. In practice those tools come from PATH, because **the embedded distribution ships only the server binaries** — even an install on the built-in database needs `postgresql-client` (`doctor` flags a missing `pg_dump`) — and the database must be running either way. Media is enumerated with `media.Store.ListObjects`, which exists only for this. A failed backup deletes its half-written archive, and the CLI won't overwrite an existing file. `restore` checks the manifest first (no manifest, or a newer `Format`, is refused) and loads the **database before the media**: rows missing an avatar are survivable, media with no rows is unreachable bytes. It **replaces everything** and makes you type `RESTORE`, refusing without a terminal unless `--yes`. Every archive entry must pass `safeName` (no leading slash, backslash, empty or dot segments), and one bad name refuses the whole archive, since entry names become object keys (tested).
- `svc/` — **running as an OS service** (`svc.go`, a thin leaf over `kardianos/service`): `bombers service install|start|stop|restart|status|uninstall`, which in practice means a systemd unit (the VPS runs as one). A **service-manager launch passes no arguments**, so `main` checks `svc.Interactive()` *before* applying the bare-`bombers`-opens-the-console default — otherwise systemd would start a console instead of a server — and hands that launch to `program` in `main.go` (`Start` returns at once; `Stop` waits up to 20s for the graceful shutdown). `Config(user)` registers `BombersServer` with **`Restart=on-failure`** and a 10s delay (on-failure rather than always, so a deliberate stop stays stopped). A failed startup **exits non-zero** instead of calling `s.Stop()`: under systemd that's a `systemctl stop` the unprivileged service user may not run, so the error was swallowed and the process sat alive serving nothing while systemd reported it running. **`service install` writes `User=`** from `--user` or `SUDO_USER` and **refuses a root-run service** (`CheckServiceUser`). Installing needs root, but embedded Postgres won't start as root and the data dir would resolve to root's home — a failure invisible until the next reboot, hence a refusal rather than a warning (`wouldRunAsRoot` is split out so the rule is tested off Linux too). `Control` checks that a unit exists before touching the service manager, so `service restart` on a server run with `bombers start` points at `bombers restart` instead of prompting for a root password over a unit nobody registered. `IsRunning` lets `bombers status` see a service-launched server, which never backgrounds itself and so writes no pidfile.
- `nodeshare/` — **friend node-sharing** (`handler.go`/`store.go`, table `node_transfers`): a lightweight inbox of node bundles sent friend-to-friend — the clone model, NOT the public node store above. A transfer is a **one-way copy**: `POST /nodes/send` (`{recipient_id, bundle}` — recipient must be an **accepted friend**, every not-allowed case collapses to an opaque `404 recipient_not_found`; 4 MiB cap), `GET /nodes/received` (my inbox, sender username joined in, newest first), `DELETE /nodes/received/{id}` (dismiss after handling — recipient only, opaque `404 transfer_not_found`). The `bundle` is the client's `{manifest, files}` node source stored as **opaque JSONB** (dumb-blob, like sync — the server never inspects it). No live link, no ownership; the recipient clones it into a project they own. Owns the same narrow `areFriends` query as `messaging`/`profiles`.
- `noderecords/` — **the people axis** (`handler.go`/`store.go`, tables `node_records` + `node_responses`): how a node puts something in front of named friends and collects what they say back. **Two sides, because nobody writes anyone else's data** (the client's hard rule): the OWNER publishes a record and names who may see it, each RECIPIENT attaches their own response, and that split is what makes it general — a record plus responses is an invite with RSVPs, a poll with votes, a shared list with additions, a challenge with everyone's results, or a "here, have this" expecting no answer. Both bodies are **opaque JSONB** (dumb-blob, like sync and nodeshare): the server does not know what an invite is, and nothing here changes when a node invents a new kind of thing to send. `POST /node-records` (`{node_id, body, audience}` — every id in the audience must be an **accepted friend**, checked as a whole so a refusal never says which one, and the record id is a server ULID), `GET /node-records/received?node=<id>` + `GET /node-records/sent?node=<id>` (newest first, each with its answers; **`?node=` is required** — a reader asks on behalf of one node, and a missing parameter is a client bug rather than a request for every node's records), `PUT|DELETE /node-records/{id}` (owner only; the update REPLACES body AND audience, so removing somebody is sending the list without them, and both nudge the union of the new and old audiences so a person just taken off is told too), `PUT|DELETE /node-records/{id}/response` (my answer, **upserted** — one response per person per record, because changing your mind is the same act again, not a second answer; `DELETE` is "I haven't said", which is not the same as answering no). Visibility: **if you can see the record you can see its responses, and the audience**, deliberately — a guest list, not a blind copy, since "who else is coming" is the question a recipient actually has. Writes nudge through `notify/` with `record` + `{"node", "from"}` so the client wakes the one node concerned. It is the **durable sibling of `rooms/`**: a room is live, in-memory and dies when it empties — right for a game lobby, wrong for an invite, which has to survive both people being offline. `node_id` is NOT a permission boundary (a user's own token reads all of their own rows); what keeps one node out of another's is that a node never holds the token. Owns the same narrow friendship query as `messaging`/`profiles`/`nodeshare`, as one batched `ANY` check.
- `imagesize/` - **the size of a picture, read from its header**, for PNG, JPEG, GIF and WebP and nothing else (`imagesize.go`; a leaf, standard library only). `Accepts(mime)` is the one accept-list for pictures (profile media and message images both ask it, so they cannot disagree) and `Dimensions(mime, data)` the width and height. It never decodes: PNG's IHDR, GIF's screen descriptor, WebP's first chunk (`VP8X` for the canvas, which is what makes an animated WebP work, `VP8L`, `VP8 `) and JPEG's marker walk to the first start-of-frame, skipping APPn/COM and 0xFF fill, and refusing to look past the start of scan. Every offset is bounds-checked and every declared length is checked against the data, so a truncated or lying file is `ErrUnreadable` and never a panic; a zero dimension is an error. `image.DecodeConfig` has no WebP and `golang.org/x/image/webp` would be a new dependency that still refuses an animated one. **`Dimensions` returns what a BROWSER WILL DRAW, not what the header stores** (`exif.go`): a phone writes the sensor's pixels and an EXIF Orientation saying how to turn them, and for orientations 5, 6, 7 and 8 (the quarter turns) the width and height are exchanged; 1-4 are returned as stored. That is the only definition that lets the client lay a box out from the payload with no knowledge of EXIF. It is read from every format that carries one, in either byte order (`II`/`MM`, with the 42 after it): JPEG's first APP1 that begins `Exif\0\0` (on the same marker walk, which now goes on past the frame header to the scan, since a decoder honours an EXIF block there too), PNG's `eXIf` chunk before the first IDAT, and the `EXIF` chunk of an extended WebP, found by stepping over the chunks before it (it follows the image data) and only when the VP8X EXIF flag is set; GIF has none. Only IFD0 is read, the tag must be one SHORT, and a value outside 1-8 is none. **A missing or damaged orientation is "none" and never an error**: no block, a byte order that is neither, a wrong magic, an IFD offset inside the header or past the end, a directory whose declared entries do not all fit, a wrong type or count, a chunk that runs off the end. A photo whose EXIF is broken still has usable dimensions, so none of it may fail the read. Offsets are `uint64` throughout, because `int` is 32 bits on the 386 build and an offset is a full `uint32`; `exif_test.go` tests with clipped capacity (`s[:n:n]`) because a window onto a file would otherwise read the bytes that follow it instead of panicking.
- `media/` — **profile media** (avatar + banner), the first slice of the S3 phase (`storage.go` the `Store` interface + minio-go S3 wrapper / `fs_store.go` filesystem backend / `store.go` metadata + narrow gating queries / `handler.go`, table `user_media`). Bytes live behind **`media.Store`** — **S3-compatible object storage** (`MEDIA_BACKEND=s3`, the default; plain S3 API only) or **plain files** under `MEDIA_DIR` (`MEDIA_BACKEND=fs`) — at the same fixed key `users/<user_id>/<kind>` either way; the `user_media` row holds sniffed content type, size, `updated_at`. `PUT /me/media/{avatar|banner}` takes **raw image bytes** (type sniffed server-side, only png/jpeg/gif/webp, the list being `imagesize.Accepts` that message images share; caps 5 MiB avatar / 10 MiB banner; 413 `media_too_large` / 415 `unsupported_media_type`), one key per (user, kind) so **reupload replaces**; `DELETE /me/media/{kind}` clears (idempotent 204). `GET /media/{userID}/{kind}` is the **authenticated pass-through**: streams bytes through the server (never a bucket/presigned URL — deliberate, per PRODUCT.md), allowed for the owner always and an accepted friend while the owner's profile visibility is `friends` (no saved card defaults to friends); every not-allowed case collapses to opaque `404 media_not_found`. ETag/If-None-Match revalidation from `updated_at`. A successful upload or delete nudges every accepted friend with a `profile` frame carrying `{"from": <uploader id>}`, so their copy of the card picks up the new picture. Startup creates the bucket (or the media directory) and is fatal if the store is unusable (mirrors the DB); `/health` gained an informational `media: up|down` field (DB still governs status). Owns narrow `areFriends` + `profileVisibility` + `acceptedFriendIDs` queries (the last a copy of profiles', for the same reason); `types.MediaURL` is the shared URL shape (`/media/{id}/{kind}?v=<unix ms>` — milliseconds, so two uploads inside one second don't share a URL) so profiles emits identical URLs without importing media. **`deluser` removes the whole `users/<id>/` prefix (`media.UserPrefix`, trailing slash so one id cannot take another's)** - avatar, banner and any kind added later - after the delete commits, in the same step and under the same removal deadline as the message pictures, best effort: a store that refuses is reported to the operator and does not undo the delete.
- `messaging/` — **direct messages**: text DMs between two users, persisted **indefinitely** in Postgres (DMs aren't ephemeral; rooms are). You may only message an accepted friend; every not-allowed case (non-friend, nonexistent, self) collapses to an opaque `404 recipient_not_found`. Owns the same narrow `areFriends` query as `profiles`. **What a person types is text, and the other kinds are minted by the server** (`kinds.go`, migration `message_kinds`): `messages.kind` is a CLOSED set — `text` (default, so every old row is text), `invite`, `image` — enforced by a CHECK and again in Go (`checkKind`, run by `insertMessage`, so nothing reaches the table with a kind, payload or body the code does not know; it is the one place that says an `invite` has no words, through `kindHasWords`), and `messages.payload` is JSONB, NULL for text. **THE RULE: a client cannot declare a kind.** `POST /messages` reads `kind`/`payload` only to REFUSE them (`400 invalid_body`; `kind: "text"` and a null payload are allowed, since they are what every send already is), and the record it stores gets `kind: kindText` — never the request's. A client able to post an `invite` with a room id in its payload would make an invite a claim in a message again, which is the `bombers://room/<id>` shortcut that was deleted. **An invite message is written by `Handler.MintInvite`, which `rooms` calls through an injected func** when it makes a NEW invite (see `rooms/` below); it is the only writer of one. Its body is `""` (the card is the payload; no server-written English to be indexed as if typed), its payload is `{invite_id, room, room_name}` with `room_name` a copy taken at send time, it is friend-gated again here, and it goes out as a normal `dm` `new` frame to both people. **An image message is written by `SendImage` (`image.go`), from bytes the server has itself read** - see "Pictures" below. Only a kind with words can be edited: text, and a picture's caption (`editableKindsSQL`, `kind IN ('text', 'image')`, is in both the lookup and the `UPDATE`, and a test holds it to `kindHasWords` over every kind), so editing a card is the same opaque `404 message_not_found` and a picture's payload is never editable; a delete clears the payload with the body and keeps the kind (and, for a picture, removes the bytes). A message has no attachments beyond the one picture an image message IS, there are no stickers and no custom emoji (a reaction is a unicode emoji and nothing else), and all of it is **DMs only**: `rooms/` chat stores nothing, so a reply, pin, reaction or search has nothing to attach to there. **Every message has the same shape on every endpoint and every frame** (`messageResponse`): `id, seq, sender_id, recipient_id, body, created_at, edited_at, deleted_at, reply_to, pinned_at, reactions, mentions, kind` — all thirteen always present (plus `payload`, the one field that is OMITTED rather than null: text and tombstones have none), with `edited_at`/`deleted_at`/`reply_to`/`pinned_at` `null` when unset and `reactions`/`mentions` `[]` when empty, so a client never has to tell "absent" from "null" from "empty". **`reply_to`, `reactions` and `mentions` are not columns, and `reactions[].me` and `mentions` are relative to whoever is reading**, so one message is not the same bytes for its two people. Every path that returns a message goes through `respond`/`respondOne`, which reads those parts for a whole page at once (one query each, and only when the page has something to resolve); a path that built `messageResponse` from `toResponse` alone would ship a message that looks unreacted-to, unreplied and unmentioned.
  - **Pictures.** `kind: "image"` is one picture, and its `body` is its CAPTION: the words a person typed under it, `""` when there are none. Its payload is `{width, height, mime, size}` and **carries no id**, because the id is the message's. **`POST /messages/image?to=<userID>[&nonce=]`** takes `multipart/form-data`: a `file` part (the bytes) and an optional `caption` part, with `to` and `nonce` staying in the query because they are addressing and not content. It answers like `POST /messages`: `201` and the message, `200` and the one already stored for a repeated `(sender, recipient, nonce)`. **It is not a second send path.** `sendTarget` (the friendship gate and its opaque `404 recipient_not_found`), `storeOnce` (the nonce lookup and the insert under `writeSeq`'s lock) and `answerSend` (the frames and the response) are the same three functions `Send` runs, and it is checked before the body is read, so a stranger cannot make the server buffer ten megabytes. **THE RULE holds:** nothing about the message is the client's word. The type is sniffed from the bytes with `http.DetectContentType` and the declared `Content-Type` is ignored; the dimensions are read out of the header by `internal/imagesize` (as the browser DRAWS them, EXIF orientation applied, so a portrait phone photo is stored taller than wide); `size` is the length of what was read; the kind is the handler's. Over **10 MiB** (the profile banner's cap) is `413 message_too_large`, a body that is none of PNG/JPEG/GIF/WebP is `415 unsupported_media_type`, and one whose size cannot be read, or that declares more than 100 megapixels (a few kilobytes of PNG can ask a client to allocate billions), is `400 invalid_image` - never stored without its dimensions, because a kind whose payload is sometimes incomplete pushes the problem into every client that draws it. **The caption is a BODY, not a kind and not a payload field.** It is read from the `caption` part by `readImageUpload` and goes through `cleanCaption`, which is `cleanBody` and nothing more: the same `plainText` scrub, trim and 1-4000 characters (`400 body_too_long`), with the one difference that nothing at all (an absent part, whitespace, or only the bytes `plainText` drops) is `""` and not `empty_body`, because a picture with no words is still a picture. There is no second copy of the rule to drift. Mentions are resolved from it on read like any body, and search indexes it. It travels WITH the bytes so that there is one message, one row and one frame, not a picture and a caption a beat later. `readImageUpload` reads the multipart off the stream (`multipart.Reader`, never `ParseMultipartForm`, which spools to disk) and takes the raw part (`NextRawPart`), under three caps: the whole request (`maxImageRequestBytes`: 10 MiB, plus `maxCaptionBytes`, which is `sendBodyLimit`, plus 16 KiB of boundaries and headers), the `file` part at 10 MiB and the `caption` part at `maxCaptionBytes` (past it is `body_too_long`, and not read on to see what `plainText` would leave). Past a cap is `413 message_too_large`. It must be `multipart/form-data` exactly (not `mixed`); a `file` part is required; each of `file` and `caption` may appear once and in either order; any other part, a `kind` and a `payload` included, is refused unread. Every one of those refusals is `400 invalid_body`, the code `POST /messages` already answers a body it does not take with, so there is no new visible code; a body that ends without its closing boundary is one of them (the wrapped `io.EOF` is compared with `==` on purpose). The checks that depend on what the parts say run after all of them are read, in a fixed order (structure, caption, then the file's type and size), so which part came first does not change the answer. `checkKind` is still the one place that says what an image may carry (`imagePayload.check`; `size` equalling the stored length is true by construction, since the payload is built from the slice that is written, and not something it can see). **The bytes live at `messages/<message id>/image`** in the same object store as profile media, which `messaging` receives from `main` as the narrow `ObjectStore` interface it declares itself (it does not import `media`; `RemovePrefix` is its only remover, on `messages/<id>/` with the slash). The key being the message's own id makes the lifetime structural: nothing can share the bytes between two messages, no request can point a message at another's picture, and every way a message ends knows where to look. **Order: bytes before the row**, because a row whose bytes are missing is a broken picture a person can see and an object whose row never landed is invisible waste. A failed insert removes the bytes - unless the row may have landed (`discardUnlessStored` asks, because an error from the commit does not say the commit failed, and with no way to ask the bytes stay) - and a removal that fails is logged and left. A repeated upload (`!created`) removes the bytes of the attempt that lost. **`GET /messages/{messageID}/image`** serves them back through the server with the caller's `Authorization` (never a bucket URL or a presigned link), `Content-Type` from the stored payload, `ETag` the message id (the bytes never change), `Cache-Control: no-store` and `nosniff`. **Only the message's two people, and only while they are still friends** (`loadParticipant` with the friend gate: history, the feed and search all omit a thread with someone who is no longer a friend, and a picture that stayed readable would be a way to keep reading it); a third party, an unknown id, a deleted message, a message that is not an image and a former friend are the same opaque `404 message_not_found`. The object is read only after all of that, under the key made from the stored row's id. A missing object behind a live row is a `500` and not a `404`: the caller may see this picture, so there is nothing to hide, and a 404 would report a bucket outage as a deletion. **A delete removes the bytes after the row commits** (the row is the commit point; the removal is best-effort and logged, because refusing the delete over a briefly unreachable bucket would refuse the one thing the person asked for). **`deluser` removes them too** (the console reads the user's image message ids before the cascade takes the rows, then removes each prefix): an account deletion cascades its messages away in the database, where no handler sees it. A picture can be pinned, reacted to and replied to like any message, and its caption (never the picture) can be edited; `PATCH` is `cleanBody`'s rule, so it can rewrite a caption but not clear one (`empty_body`). A reply to a picture previews its caption, or an empty body when it has none: `reply_to` carries no kind, so it cannot yet say "a picture" (adding `kind` to the preview is the real fix, and is not built). `internal/backup` walks every key under the empty prefix, so these ride along with no change (`media/` in the archive; checked, not assumed).
  - **TWO CURSORS, and never confuse them.** `seq` comes from one global sequence (`messages_seq`), is assigned on insert and **assigned AGAIN on every change to a message — an edit, a delete, a pin, an unpin, a reaction added, a reaction removed**; it is for the **catch-up feed only**. A change moves it, so `seq` order is *not* message order — sorting a conversation by it would put an edited, or merely reacted-to, message at the bottom. A conversation is ordered by `(created_at, id)`, and **history, the conversation list, search and every `?before=` page on that**, never on `seq`. The reverse mistake (catching up by `id`) would miss every edit, delete, pin and reaction. A reaction is a row in another table and changes nothing on the message, so `touchMessage` exists only to draw its `seq`: that bump is the one thing that carries a reaction to a client that was offline, and a second sync path for reactions and pins is precisely what must not be built. The cost is that a reaction on an old message puts it in the feed looking new, which a client holding a window of recent messages has to refuse to insert as a gap.
  - **Writes that draw a `seq` run through `writeSeq`**, which takes a transaction-level advisory lock (`seqLockKey`) before `nextval()` and holds it to commit. A sequence hands out numbers in the order writes START, but a client's cursor is only safe if rows become VISIBLE in that order — otherwise a write that drew 10 and lost the commit race to one that drew 11 is invisible to a client already at 11, and its cursor never goes back. Chat-sized traffic makes the serialising free. `insertMessageSQL` stamps `created_at` with `clock_timestamp()`, not the column default `now()`: `now()` is the transaction START, which can sit tens of milliseconds before that transaction's commit, so a message could be stamped earlier than one that committed ahead of it. `clock_timestamp()` is read inside this same advisory lock, so `created_at` order matches `seq` order and commit order — which a read position (below) depends on. `pinned_at` is `clock_timestamp()` for the same reason (so the order pins are listed in is the order they committed); `edited_at` and `deleted_at` still use `now()`. Every send, edit, delete, pin, unpin and reaction goes through `writeSeq`, and so do the reads that decide whether to write — the pin cap, the two reaction caps, the repeat check — which run INSIDE the lock so that two concurrent writes can't both see room for one more.
  - **Send/edit/delete.** `POST /messages` takes an optional `nonce` (trimmed, ≤ 64 chars, else `400 nonce_too_long`), echoed in the `201` and the `op:"new"` frame so the sender's client replaces the row it drew optimistically; the nonce is also stored (write-only; no SELECT reads it back; an empty one is `NULL`, never `''`) behind a partial unique index on `(sender_id, recipient_id, nonce)`, so a repeat send returns the message already stored **as it is now** (an edit or delete since is part of the answer) with **`200` instead of `201` and pushes nothing** — a retry after a lost response can't send twice. `insertOnce` looks the nonce up BEFORE inserting, inside `writeSeq`'s lock: `ON CONFLICT DO NOTHING` would still draw a `seq` for the losing insert and leave a hole in the catch-up numbering, so the unique index is only the backstop. The repeat is still validated and friend-gated, and matches on `(sender, recipient, nonce)`: a different body under that key returns the original, but the same nonce to a different recipient is a new message (`201`, delivered) — the recipient is in the key because a retry always has the same one, and without it a reused nonce would hand back the first person's message and never deliver to the second. `PATCH /messages/{messageID}` (`{"body"}`, same trim/empty/4000 rules as send via the shared `cleanBody`; the body of a text message, or the caption of a picture) sets `edited_at` and a new `seq`, → `200` with the message; `DELETE /messages/{messageID}` → `204`. There is **no edit window**. Both are **sender-only through one SQL `WHERE` (`id`, `sender_id`, `deleted_at IS NULL`)**, so a missing message, someone else's and an already-deleted one are the same zero rows → the same opaque `404 message_not_found`. A delete is a **tombstone**: `body` is overwritten with `''` in the database (the words are deleted, not hidden), `deleted_at` is set, and the row stays so the catch-up can tell a cached client, and the pin, the reply link and every reaction row go with the words (a tombstone says nothing; replies others made to it keep their link and so preview it as deleted). **`PATCH` is friend-gated; `DELETE` deliberately is not.** `Edit` runs in a fixed order: `cleanBody`, then `ownMessageRecipient` (a lookup scoped to `id AND sender_id = caller AND deleted_at IS NULL`), then `guardRecipient`, then the write. A non-sender, a missing message and a deleted one are refused at the lookup and never reach the friendship check, and every refusal — a failed friendship check included — is the byte-identical `404 message_not_found`. An edit ADDS words to a thread, so it needs the friendship sending needed. A delete only removes the sender's own words and its frame carries no body, so being unfriended or blocked must not stop someone taking their own words back; that asymmetry is intended, so don't add a gate to `Delete`.
  - **Replies.** `POST /messages` takes an optional `reply_to_id` (`messages.reply_to_id`, `ON DELETE SET NULL`: a reply must outlive what it answers — though a delete is a tombstone and the row is never actually removed, so in practice the preview reports `deleted: true`). It must name a message of THIS pair, in either direction, deleted or not; anything else — another conversation's message and a nonexistent id alike — is `400 bad_reply`. **That check is a security boundary, not politeness:** `reply_to` is a preview of the original's first 120 characters, so without it a reply is a way to read a line out of a conversation you are not in. It runs after the friendship gate, so a stranger learns nothing from it, and `replyPreviewsSQL` insists the original and the reply share a pair again at read time, so a wrong row still could not leak a line. The preview is **resolved when the reply is read and never stored**, so an edit of the original shows through. **`reply_to_id` is written by `insertMessageSQL` and nowhere else**, and `Edit` never reads it — that, not a check, is what makes it immutable, so no UPDATE may ever set it. A delete clears the tombstone's own link; replies *to* it keep theirs.
  - **Pins.** `PUT|DELETE /messages/{messageID}/pin`, `GET /messages/{userID}/pins`. **Either person may pin or unpin either person's message**: a pin is a property of the conversation, so unlike edit and delete it is not sender-only (`participantMessage` matches sender OR recipient). Pin and unpin are both friend-gated, and every refusal — missing, deleted, between two other people, partner no longer a friend — is the same opaque `404 message_not_found`. **At most 50 per conversation** (`400 too_many_pins`), counted over the pair in either direction: an uncapped list is a list nobody can use, and the cap is what makes the list bounded by construction (its `LIMIT` is the cap), so it needs no paging. A repeat — pin what is pinned, unpin what isn't — is a `200` that draws no `seq` and pushes nothing: the lookup before the UPDATE and the `pinned_at IS [NOT] NULL` in its `WHERE` both make that so, and a repeat at the cap is still that success. `pinned_by` is written with the pin and never read: in a two-person conversation it says nothing a client needs, so it has no field and is not returned. A delete clears the pin, so the list never holds a tombstone. `messages_pinned_idx` is a partial index on `pinned_at` that serves the list and the count; the obvious `(recipient_id, sender_id, pinned_at)` would be the wrong shape for a pair matched in both directions.
  - **Reactions.** `PUT /messages/{messageID}/reactions` (`{"emoji"}`) and `DELETE …/reactions/{emoji}` (percent-encoded in the path; `RemoveReaction` unescapes the segment itself because chi returns it raw or already decoded depending on the escape). One row per `(message, user, emoji)` in `message_reactions`, `ON DELETE CASCADE` since a reaction means nothing without its message. **Adding is friend-gated and removing is not**, for the reason `Delete` isn't: a reaction is your own mark, and being unfriended or blocked must not strand it on someone's message forever. Removal still requires being a party to the message, and its `react` frame still goes to BOTH people, a former friend included — they could not learn of it any other way, because that thread is not in their catch-up feed. Adding what you already added, or removing what you never added, is a `200` that draws no `seq` and pushes nothing, which is what makes a double-tap and a retry safe. **Both caps — 20 distinct emoji and 50 reactions in all per message (`400 too_many_reactions`) — exist so the field cannot become a second message body**; they bind only a reaction that would be NEW, so a repeat at the cap is still the no-op success and an emoji somebody already used does not count against the 20. Nothing can be reacted to once deleted (`404`), and a delete removes the message's reaction rows. `reactions` is ordered by when each emoji was first used. The emoji is validated before the message is looked up, by the one function (`cleanEmoji`) that add and remove share so the two can't drift.
  - **`cleanEmoji` is two clauses, and each does one job.** A reaction must be **exactly one grapheme cluster** (`rivo/uniseg`, i.e. Unicode's extended grapheme clusters — a flag, a skin tone, a ZWJ family, a subdivision flag and a keycap are each one), and every rune of that cluster must be an **emoji-making rune**. The CLUSTER clause keeps WORDS out: any number of separate emoji, letters or words is several clusters, whatever script they are in (`ⓗⓘ`, a braille word, two flags, a row of ideographs). The CHARACTER clause keeps TEXT out: each rune is a symbol (`unicode.So` at or above U+0100, excluding U+FFFD, which is itself `So` and is what invalid UTF-8 decodes to), a skin-tone modifier (U+1F3FB–1F3FF, which are `Sk` and so named by range because `Sk` as a class would admit `^`, the backtick and the Latin-1 accents), one of the ten code points in `emojiOutsideSymbols`, glue (ZWJ, U+FE0E/FE0F, U+20E3, tag characters U+E0020–E007F), or an ASCII digit/`#`/`*` that is the FIRST rune of a keycap sequence; letters and numbers of any script, whitespace, punctuation, marks, controls, math and currency symbols are refused, and so is a cluster of only glue. The trimmed value is capped at 16 runes and 64 bytes, because a ZWJ chain can be one cluster of any length (the byte cap cannot bind while the rune cap is 16, and is kept as the bound that survives raising it). **The ten named code points** — `ℹ ‼ ⁉ 〽 〰 ↔ ⤴ ⤵ © ®` — are real emoji Unicode files outside `So`, or inside it but below the U+0100 floor that keeps `°` and `¦` (typography) out. To add another, add ONE entry to `emojiOutsideSymbols`; do not widen the rule to a whole category (`Sm` would admit `=`, `+` and `|`) and do not start a list of excluded blocks or ranges again — the cluster clause replaced exactly that. **A single unusual symbol is accepted on purpose** (one enclosed ideograph, one braille cell, one circled letter): the rule exists so the field can't become a second message body, and one character is not a body. Don't "fix" it. `uniseg` is a direct dependency, but it was already in the module graph (`lipgloss` pulls it in), so no new code entered the build. A client's picker must offer real emoji and treat `bad_emoji` as the answer, never copy the rule.
  - **Mentions.** A mention is `<@userid>` in the body — the id, not a name, because a name breaks the moment someone is renamed and is ambiguous between two friends who share one. The server matches `<@([A-Za-z0-9]+)>` (`mentionPattern`) and reports ids in `mentions`: each once, in first-appearance order, at most 16, and **only ids that are the reader or one of the reader's accepted friends** (`mentionableSQL`, through the same `acceptedCTE` as everything else that asks who a friend is). An id that is neither stays in the text and is simply not reported — never an error, because failing a send over something that merely looks like a mention would be worse than ignoring it. `mentions` is **derived on every read and never stored**, so an edit that removes one removes it everywhere, and it is relative to the reader: a friend of mine is not necessarily a friend of yours, so the two people can be told different things about one message. A client draws a person only for an id the server reported; drawing one for every well-formed `<@id>` would let anyone fake a mention of anybody by typing the characters. Mentioning notifies nobody. Formatting (bold, code, quotes, links) is not the server's: the stored body is plain text, the server never parses it, and search indexes it as typed.
  - **Search.** `GET /messages/search?q=&with=&before=&limit=`. `messages.body_tsv` is a **generated** `tsvector` (`to_tsvector('english', body)`, GIN-indexed), so it can never drift from `body` — an edit updates it with no trigger and nothing to remember — and a tombstone (`body = ''`) has an empty vector. The query still states `deleted_at IS NULL`, so "a tombstone never matches" does not rest on the body having been cleared. **The two-argument `to_tsvector` is required**: a generated column must be IMMUTABLE, and the one-argument form depends on a setting and is rejected. `q` goes through `websearch_to_tsquery('english', …)`, which takes what a person actually types (quoted phrases, `-exclusions`, `or`) and **never raises on punctuation, where `to_tsquery` would** — a search box must never be a 500; a query with no searchable words is an empty tsquery that matches nothing, a `200` with an empty list. Matching is whole stemmed words, not prefixes. `q` is `plainText`, trimmed, 1–200 characters (`400 empty_query` / `400 query_too_long`). **Friends-only through `acceptedCTE`** — the third reader of that CTE after the catch-up feed and the conversation list, so there is still one definition of "my friends" — with the peer filter inside each of two unioned branches before its `LIMIT`, so a former friend's messages can't use up a page. `with` narrows to one conversation; a non-friend or yourself is the opaque `404 recipient_not_found`. **Ordered `(created_at DESC, id DESC)`, never by relevance and never by `seq`:** chat search means "when did we talk about this", and a relevance order makes a conversation unreadable. `before` is keyset on a message's `(created_at, id)` — through `historyCursor` when `with` is given, `inboxCursor` otherwise — and an unusable one is `400 bad_cursor`. `limit` is 50/max 100, and `has_more` is "the page filled", matching history rather than an exact limit+1.
  - **No text anyone can type may be a 500.** Postgres refuses invalid UTF-8 and NUL in a text parameter, and a refused statement is a 500. `plainText` drops both BEFORE any trim or length count — so a body of nothing but those bytes is judged empty rather than stored blank — and is the one door for everything a person supplies that reaches a statement: bodies (`cleanBody`, which a picture's caption goes through too, as `cleanCaption`), queries (`cleanQuery`), nonces, the reply target, and, through `urlParam`/`queryParam`, every id and cursor in a path or query string. A new handler in this package reads those through the two helpers, never through `chi.URLParam` or `Query().Get` directly. Only `internal/messaging` has this; no other domain's `before` or id parameters have been swept.
  - **Reading.** `GET /messages?since=&limit=` is the **catch-up feed** — everything I sent or received with `seq > since`, `seq` ascending, **tombstones included**; `since` missing/negative/garbage → 0; limit 200/max 500; returns `{messages, cursor, has_more}` (`cursor` is the highest `seq` on the page, or the requested `since` when empty; `has_more` is "the page filled", so it can be true on a last page that turns out to be followed by an empty one). Written as a `UNION ALL` of two indexed reads (`messages_sender_seq_idx`, `messages_recipient_seq_idx`), each branch capped at the page size, rather than an `OR`. It is **friend-gated**: `listUpdatesSQL` restricts each branch, before its `LIMIT`, to the `accepted` CTE (`recipient_id`/`sender_id IN (SELECT peer_id FROM accepted)`), the same `acceptedCTE` the conversation list uses, so there is one definition of "my friends" and a thread with someone unfriended or blocked is absent (matching history's `404` and the list dropping them). `GET /messages/{userID}?limit=&before=` is history: newest page, or strictly older than the `before` message id, keyset on `(created_at, id)` through an anchor read (`historyCursor`, which scopes the id to the pair and deliberately ignores `deleted_at` — a tombstone is still a place to page from); **`?around=<message id>` on the same route is the page CENTRED on a message** (how a search hit, a pin or a reply's original older than the loaded window is opened without paging back to it): the older side gets `(limit+1)/2` places INCLUDING the anchor when it is live, the newer side gets `limit` minus that, so a page never exceeds `limit` and `limit=1` is the anchor alone; at the newest or oldest message the page is short on that side and is NOT refilled from the other; a tombstone anchor positions the page and is never returned; the response is **`{messages, has_more_older, has_more_newer}`** because two directions cannot share one flag (each true exactly when the page stops short of that end of the live conversation), and `?before='s `{messages, has_more}` is unchanged; `around` with a non-empty `before` is `400 conflicting_cursors` (checked after the friend gate; an empty one counts as absent) and an `around` naming no message of the pair is `400 bad_cursor`. It is two keyset reads on `(created_at, id)` (`listAroundOlderSQL` `<=` the anchor descending, `listAroundNewerSQL` `>` it ascending, never `seq`), each fetching one row past its places to set its flag; **tombstones omitted**; ascending; limit 100/max 200; `{messages, has_more}`; a `before` naming no message of the pair is `400 bad_cursor` (an error, not an empty page, which would read as "nothing older"). `GET /conversations?limit=&before=` is the inbox: **one SQL statement** (`listSummariesSQL`: `accepted` friends CTE → `exchanged` two-branch union of live messages → `DISTINCT ON (peer_id)` newest → left joins to the `unread` tally and to both directions of `message_reads`), no per-friend loop; entries are `{user_id, last_message, unread, my_read_at, my_read_id, peer_read_at, peer_read_id}` (all four always present, `null` when unset; the pair is the whole read position), newest conversation first, limit 50/max 200, `{conversations, has_more}`; **only accepted friends**; a pair whose every message was deleted is absent; `before` is keyset on a message's `(created_at, id)` and accepts any message the caller sent or received (`inboxCursor`), anything else `400 bad_cursor`.
  - **Unread is server-authoritative** and has ONE definition (`unreadMessagesSQL`, shared by `GET /messages/unread` and the conversation list's `unread`): messages I received, **not deleted**, sorting after my `message_reads` position for that sender: `(m.created_at, m.id) > (r.last_read_at, COALESCE(r.last_read_id, ''))`. `GET /messages/unread` is unchanged (`{ conversations: [{ user_id, count }], total }`). **A read marker is a POSITION, not a clock reading:** `last_read_at` is the `created_at` half and `last_read_id` the id half, of the newest message actually read from that peer, copied out of `messages` by the statement itself. A clock marker was wrong because `now()` is the transaction start: a message stamped T could commit at T+30ms, a marker taken at T+10ms then classed it as already read, and it was never unread. **There is deliberately no backfill, and none may be added:** a row written before `last_read_id` existed has it `NULL`, `COALESCE(…, '')` sorts below every ULID, so such a row keeps meaning "everything up to that instant is read", and guessing an id for it would pick a message the reader may never have seen. `POST /messages/{userID}/read` moves the marker to the newest non-deleted message that peer sent me → `204` in every case; with nothing from the peer to read it writes nothing, advances nothing and **pushes nothing**, so opening an empty conversation is not an event. The marker is advanced **monotonically** (the upsert's `WHERE` refuses to move it backwards and `RETURNING` yields nothing when it didn't move) — which is also how the handler knows whether to tell the peer. A missing/self `{userID}` is a `400`. The marker is a personal bookmark and is not friend-gated; **the read receipt is**: when the marker moved AND the two are accepted friends the peer gets a `read` frame `{from, at, id}` (the stored position); an unfriended target gets nothing, or this route would push a frame to any user id.
  - **Typing.** `POST /messages/{userID}/typing` → `204`, friend-gated with the same opaque `404 recipient_not_found`, stores nothing, pushes `typing` `{from}` to that peer only. The server does not throttle it (there is no API-wide rate limiter; the client sends at most one per 3s).
  - **Live delivery carries the message.** After a write is stored, `pushDM` hands `Notify` a `dm` frame `{op: new|edit|delete|react|pin, from: <the message's sender>, message, nonce?}` for **both** the recipient and the sender, so the sender's other windows and devices stay in step. **It is one frame per PERSON, not one shared frame:** `reactions[].me` and `mentions` are relative to the reader, so a single payload cannot be right for both, and `pushDM` builds the message for each and calls `Notify` once for each. `from` is always the message's author, never whoever acted (a pin or a reaction can be by either person), and nothing routes on it — a client finds the conversation from the message's own `sender_id`/`recipient_id`. `pin` and `react` cover both directions: the message in the frame is the state as it now stands, and the frame does not say pinned-or-unpinned or added-or-removed. A write that changed nothing — a repeated pin, a reaction already there or never held — pushes nothing. The frame is pushed after the commit, never before. `Notify` is a `func(userIDs []string, kind string, data any)` field injected from `main.go` as `notifyHub.SendMany` — messaging never imports `notify/` — and nil means nobody is listening (how tests build handlers). The domain's `KindDM`/`KindTyping`/`KindRead` repeat the `notify` values, since it can't import them; `cmd/bombers/messaging_wiring_test.go` pins the two sets together. There is still **no offline queue**: the durable copy is the row, and a client that missed frames closes the gap with the catch-up feed. `handler_test.go` and `store_test.go` cover the clamps, sender-only/opaque 404, tombstones in the feed and out of history, unread ignoring deleted messages, both ids notified, no push when the marker doesn't advance, the nonce, and for the chat features every shape `cleanEmoji` refuses, each cap, the no-op repeats, `me` and `mentions` per reader, the reply boundary, search's friend gate and keyset, and that a reaction or a pin reaches the catch-up feed.
  - **Token scopes.** Everything that *does* something as you is `messages:write` — `POST /messages`, `PATCH`/`DELETE /messages/{messageID}`, `PUT`/`DELETE /messages/{messageID}/pin`, `PUT /messages/{messageID}/reactions`, `DELETE /messages/{messageID}/reactions/{emoji}`, `POST /messages/{userID}/read` and `/typing` (the scope reads "Send, edit and delete direct messages as you, pin messages and react to them, and show friends when you're typing or have read their messages" — a pin and a reaction are each you putting something in front of a friend, and a read receipt and a typing indicator are each you telling one something, so a read-only token may make none of them; `/read` used to sit ungated in the auth group and moved here). Everything that only looks is `messages:read` ("Read and search your direct messages, who you've talked to, and what's been read") — `GET /messages`, `/messages/unread`, `/messages/search`, `/messages/{userID}`, `/messages/{userID}/pins`, `/conversations`. `/messages/search` and `/messages/unread` are static routes registered ahead of `/messages/{userID}` so they win over it.
- `notify/` — the **nudge socket** (`notify.go` hub / `handler.go` socket; no table): a per-user WebSocket that says "something you care about changed". **The rule is that it carries no content** — a frame is the room envelope `{t, d}` naming what changed and whose, never the thing itself — so the client re-reads through the ordinary endpoints, which already decide who may see what; the package needs no permission model of its own and can't leak anything by nudging the wrong list. **`dm` is the deliberate, stated exception** (the package comment says so): it is addressed to exactly the two people in a conversation, whose ids come from the message row itself, so there is no broadcast list to get wrong — and a chat that makes you fetch after every doorbell is not a chat. `messaging` builds the frame and decides who gets it; this package still only delivers what it is handed. Seven kinds: `dm` (`{op: new|edit|delete|react|pin, from: <the message's sender id>, message: {...}, nonce?}`, to BOTH people once `messaging` has stored the write — but as one frame per person, built separately, because the message carries `reactions[].me` and `mentions` that are relative to the reader and a shared payload would hand someone else's view; `react` and `pin` carry the whole message as it now stands and say nothing about add-or-remove or pin-or-unpin; `nonce` only on `new` and only if the sender gave one), `typing` (`{from}`, to the one friend being typed at), `read` (`{from, at, id}` — `at` and `id` are the reader's new position — to the one friend whose messages were read, only when the reader's marker moved), `profile` (`{"from": <owner id>}`, to every accepted friend after `PUT /me/profile` or a media upload/delete), `friend` (no `d`; to the target of a request, to the requester when it's accepted or rejected, and to the other party on an unfriend) and `record` (`{node, from}`, from `noderecords`). **`invite`** (the whole invite from `rooms/`, `{id, room, room_name, from, from_name, to, to_name, state, expires_at}` — a second kind that carries content, for the same reason as `dm`: it is addressed to exactly the person asked, or the person who asked, and `rooms` builds it from the invite itself; `state` says which change it is — `pending` to the invitee on creation, `accepted`/`declined` to the inviter and the answerer, `expired` to the invitee alone when a pending invite lapses (its room ended, or its hour ran out) — and it is only a nudge, since `GET /invites` lists what is waiting). `GET /notify/ws` sits OUTSIDE `RequireAuth` like the room join, for the same reason: the access token rides the **`bearer` subprotocol** and is verified with the same issuer (bad/missing → `401`). Separate from `rooms/` because the two share only the transport — a room socket is scoped to a room and dies with it; this one is scoped to a person, and the `Hub` keeps a SET of sockets per user so two windows or two machines all get told. **Best-effort by design**: `Send` never blocks or errors, a connection's 16-frame queue drops when full rather than slowing the write that caused it, nothing is queued for an offline user, and the server pings every 25s and drops a connection whose pong doesn't come back within 60s (a sleeping laptop never closes its socket). Anything a client sends is ignored, never refused. `Hub.Send` takes one user and `SendMany` a list; no domain imports the package — `main.go` hands `friends`/`profiles`/`media`/`noderecords` small funcs and `messaging` the hub's `SendMany` directly (nil = nobody listening, which is how the tests build handlers). `notify_test.go` covers fan-out to every socket, addressing, the full-queue drop, deregistration and the nil hub.


- `transfers/` — **the ICE list for a peer-to-peer file transfer** (`ice.go`; no table). The bytes never touch this server — the two clients open a WebRTC data channel between themselves, over a `rooms/` room where they found each other — so the one thing they need from here is the STUN servers to find a route with. **`GET /ice`** answers `{"iceServers": [{"urls": [...]}]}` from `ICE_STUN_URLS` (default: `stun:stun.l.google.com:19302` and `stun:stun1.l.google.com:19302`, the list the client carried before the server handed one out), behind `RequireAuth` and unscoped for tokens (it reveals nothing about anyone). **STUN only, never TURN** — a TURN server relays every byte of a transfer, which is the metered bandwidth the peer-to-peer design exists to avoid, so two peers that cannot reach each other fail and say so instead of being quietly relayed at the operator's expense. That is enforced, not documented: `ParseSTUN` (run by `config.Load`, at the very start of boot) refuses `turn:`/`turns:` and any other scheme, bad host or bad port, and `NewHandler([]string)` checks every entry again so a list built by anything else cannot smuggle one in, the response type has no username/credential fields, and `ice_test.go` pins all of it. Serving the list from here also means a self-hosted island need not depend on anyone else's STUN. **There used to be a `POST /transfers/offer` here** (a `transfer` nudge telling one friend a file was coming); the owner chose a join-a-link flow instead — both people join a live link first and send from inside it — so it was removed, and with it the `transfer` notify kind. Do not bring back a "tell an absent friend about a pending file" endpoint: joining the link is the consent, and offline offers are what he rejected.

- `rooms/` -- the **realtime relay** behind games and lobbies, the first WebSocket domain (`github.com/coder/websocket`). **The server never learns a game's rules**: it forwards opaque `{t, d}` frames between the members of a room and tracks presence, nothing more. **A room is not a game** -- it's a temporary space with a name, some people, and an activity id the HOST sets from inside it over the socket (`POST /rooms` names no activity and generates a name like `amber-lantern` if you don't). The creator is the host and **the host seat never transfers**: they rename, kick, choose the game and end it, and their leaving ends the room for everyone. A dropped socket is not a decision, so the host gets the same 2-minute grace as anyone and the reaper closes the room only if they don't return; `host:end` closes it at once. Two reserved namespaces in opposite directions: `room:` (server → client presence + facts: `welcome`/`join`/`leave`/`update`/`kicked`/`closed`/`error`; `welcome` and every `update` carry `{name, activity_id, member_invites}` — `update` is built in one place, `updateLocked`, so a rename, a game change and the invites switch can never disagree about which keys a frame has) and `host:` (client → server host-only requests: `rename`/`game`/`kick`/`end` and `invites` (`host:invites {"allow": true|false}`), answered and never relayed; anyone else gets `not_host`). Move validation, scores and a late joiner's state resync stay client concerns. Rooms are **in-memory and ephemeral** (DMs persist forever, rooms persist nothing): `GET /rooms/{roomID}/ws` joins one, and `GET /rooms/{roomID}` (inside the auth group) says whether one is still open — `{id, name, host_id}` under the same gate (`allowed`, shared with the join) and the same opaque 404 — it used to be how a DM invite chose between a Join button and "Room closed"; an invite now carries its own `state`, so nothing here depends on it. That join sits OUTSIDE the `RequireAuth` group on purpose -- a webview can't put an Authorization header on a socket, so the access token rides the **`bearer` subprotocol** and the handler verifies it with the same issuer. **The join gate is ONE function, `Handler.allowed`, and it is the only place that decides who may reach a room** (the socket join and `GET /rooms/{roomID}` both call it, as does nothing else): you may if you are the host, OR an accepted friend of the host, OR the holder of an ACCEPTED, unexpired invite to THIS room. Every refusal is the opaque `404 room_not_found`. **The third clause is the security-relevant one, and an invite is a deliberately narrow credential**: it names one room (each room checks only its own invites, so another room's accepted invite admits nobody here), it lasts an hour (`ExpiresAt`, checked against the clock by `Room.HoldsInvite` itself, because an accepted invite never changes state when its hour passes and so cannot be left to whatever last read it), it dies with the room (`HoldsInvite` refuses once the room is closed, independent of `hub.Get` already hiding a closed room), the host opted in (an invite to someone the host does not know can exist only because `member_invites` was on when it was made), and a member vouched for the holder (inviter and invitee are accepted friends). Only `accepted` counts: `pending` is an offer, and `declined` or `expired` admit nobody. Switching `member_invites` back off evicts nobody and does not void an accepted invite; it only stops new ones being made, and `kick` is what removes a person. **A kick VOIDS the kicked person's invite to this room**: their pending or accepted invite becomes `declined` (the existing final state, not `expired` and not a new one), so a stranger to the host — for whom the invite is the only way in — cannot walk straight back; accepting it again is `409 invite_answered` and re-inviting returns the declined one. It touches only that person's invites to THIS room (not their invites to other rooms, not anyone else's), the inviter and the kicked person are both sent the declined invite as one frame like any answer, and a kick with no invite in play sends nothing. **A friend of the host is admitted by the friendship, so for them a kick still removes only for the moment. That asymmetry is deliberate: a kick is not a ban, making it one is a different feature nobody has asked for, and `Room.Kick` says so in a comment so nobody "fixes" it.** **The target need not be connected**: `Kick` succeeds for someone ABSENT who holds a pending or accepted invite to the room (they are exactly who a host most needs to remove, being the one who can walk back in), voiding it and sending nothing to a socket that is not there — no `room:kicked`, no `room:leave`, the roster untouched; the invite frame tells both ends. It still refuses (`refused`) when there is genuinely nothing to do — not a member, and no pending or accepted invite (a declined or lapsed one is nothing to revoke). The refusal used to be right because kick only closed a connection; it went stale when kick began revoking a credential. The host has no list of absent holders to press kick on in the GUI (a roster of invited-but-absent people is a UI decision, not built); the terminal verb takes a name, so it works there. The invite is checked before the friendship because it is memory against a database query, and so that a failed friendship check cannot shut out a valid invite. `hostRelation` (host, or friend of the host) is the host's side of that function, not a second gate: `mayInvite` asks it directly because, with the switch off, who may be invited is exactly who needs no invite to get in. **An accepted invite is NOT counted there** — it would let a member re-invite a stranger a past invite let in and so extend their stay past the hour with the switch off. And an accepted invite is never forgotten to make space under the 64-invite cap while its hour has not run out (`forgetSpentInvitesLocked`), because it is the holder's way back in. Per-member **token-bucket rate cap** (burst 120, 60/s -- sized so 30Hz position sync for a 3D activity never trips it) drops the message and tells the sender rather than closing the socket; a slow peer's frames are dropped instead of stalling the room; frames cap at 64 KiB; the `room:` type namespace is reserved so a client can't forge presence, and `from` is stamped server-side so it can't be spoofed. An empty room is reaped after a 2-minute grace (so a reconnect, or the gap between create and socket, survives). The hub is testable without a network via the `Sender` seam -- `hub_test.go` covers presence, the host seat never transferring, rejoin-replaces-connection, the rate cap (including a 30Hz stream), reaping, and the spoofing guards.

  **Room invites** (`invites.go`/`invites_handler.go`; no table, **no migration, and there must not be one**): "come to my room", held by the server. **An invite is owned by its ROOM, in memory, and dies with it** — it points at a room, rooms are ephemeral, and a Postgres row would outlive the one thing it points at and be garbage on every restart. What made the old invite a shortcut (a `bombers://room/<id>` string regex'd out of DM text — **that mechanism is gone and must not come back**) was never where it lived but that the server held no state: no record, no expiry, no author, and anyone who typed the string got in. Routes: `POST /rooms/{roomID}/invites {"user_id"}` → the invite (`201` new, `200` when the person already has a pending one — **the same invite, not pushed twice** — or has declined, **which is final for the room's life**: the declined invite comes back, never a fresh one), `GET /invites` → `{"invites": [...]}`, **pending only**, newest first, across every room, `GET /invites/{inviteID}` → the invite as its inviter OR its invitee reads it, in ANY state (the read behind a card in the DM thread; `inviteIndex.byID` is the second locator it needs, kept in step with `byUser` by `add`/`drop`; anyone else and an unknown or pruned id are the same `404 invite_not_found`, which the card reads as EXPIRED), `POST /invites/{inviteID}/accept` → `{"room": "<id>"}` and `POST /invites/{inviteID}/decline` → `204`. **Every NEW invite also gets its card: `CreateInvite` calls the injected `MintInviteMessage` (wired in `main` to `messagingHandler.MintInvite`; `rooms` never imports messaging) after `Room.Invite` returns `created` and BEFORE the invitee is pushed.** This is NOT a transaction — the invite is in memory and the message in Postgres — it is compensation: if the message cannot be written the invite is VOIDED (`Room.VoidInvite`: removed from the room and both indexes, any queued news about it dropped, nobody told; not a decline and not an expiry), the inviter gets a `500`, and asking again makes a fresh one. So there is never an invite without its card; the reverse (a card whose invite is gone after a restart, the room ending or the sweep) is allowed and correct. A re-ask (`created == false`) and every refusal write no message. The write runs under `context.WithoutCancel` so a client hanging up cannot leave an invite without its card. **Persisting invites to make this a transaction is the thing not to do** — see the heading of this section. **Accepting joins nothing**: it marks the invite and hands back the room id, and the client opens the socket through the unchanged join gate. An invite is `{id, room, room_name, from, from_name, to, to_name, state, expires_at}` (`to`/`to_name` are beyond the original plan: the inviter is told of an answer and must be told by WHOM) with `state` one of `pending`, `accepted`, `declined`, `expired`; `room_name` is the room's name at read time. **Any MEMBER in the room right now may invite**, not only the host. The inviter and invitee must be accepted friends, AND the host's **`member_invites` switch** (default OFF, set by the host with `host:invites`, rides `room:update`, carried in `room:welcome`) decides the rest: OFF means exactly what it always did — the invitee must also be the host or the host's friend (`hostRelation`), otherwise the invitation could only end in a 404 at the socket; ON means any member may invite their own friends, strangers to the host included, and the join gate then admits them on the strength of the accepted invite (see the gate above). The room re-reads the switch under its lock (`Room.Invite`'s `needsSwitch`, `ErrInvitesOff`), so an invite authorised on a switch the host turned off while the friendship query ran is refused, not created late. The refusal is still the same opaque 404 whatever the reason — the client explains itself from the flag it already holds; **every refusal is the same opaque `404 room_not_found`** as the join gate (no room, ended, not a member, self, not a friend, not admissible), `400 invalid_body` for a missing `user_id`, `400 too_many_invites` past 64 remembered per room. Answering: `404 invite_not_found` (unknown, or not addressed to you — indistinguishable), `409 invite_answered`, `410 invite_expired`. **Expiry is lazy and has two causes: one hour after the invite was made, and the room ending.** There is no timer — `settleLocked` is consulted on every read and turns a pending invite into `expired`, and `Room.Close` also settles every pending one itself, so a pending invite to a dead room can never read as pending whichever path closes it. **`expireLocked` is the ONE place a pending invite becomes expired**, and it is where the invitee is owed a frame (below). **Locks**: an invite lives in `Room.invites` under the room's `mu`, like everything else on a room. `GET /invites` is per-user across rooms, so the hub keeps `inviteIndex` — a *locator* (invitee → invite id → room), with its OWN lock, never the hub's — and the invite itself is not copied into it (one copy of the truth). Order is `Room.mu` → index lock and never the reverse; the index never calls into a room while holding its lock, and nothing in this feature takes the hub lock (`Hub.Get` already releases it before touching a room). The reaper's sweep drops index entries past their hour (`lapsed` lists them without removing, each room is settled, then `drop` removes exactly that list — **tell first, forget last**, or the id would later read `404 invite_not_found` to someone never told it expired), so an ended room's invites read `expired` until then and the room is collectable afterwards. **Delivery**: notify kind `invite` carrying the whole invite — to the invitee when one is made, and when it is accepted or declined to BOTH the inviter (who learns the answer) and the answerer (so their other windows settle on it instead of showing a pending invite that would now 409) — one frame value built once from the settled invite and sent to both, never two pushes that could disagree. **The invitee is also told when an invite EXPIRES** (`state: "expired"`, same invite object: `copyLocked` is the one place an invite is copied out, for response bodies and frames alike) — when the room closes (host `end`, the reaper closing an empty or hostless room) and when the hour runs out, and also when a read happens to notice first (a re-ask, a list, an answer), because the transition is what is announced, not the path to it. **Only invites that were `pending`** (an accepted or declined invite never becomes `expired`, so a settled answer is never contradicted), **once per invite** (the pending→expired transition happens once, so a room that closes and is then reaped sends one frame, not two), **to the invitee only** (the inviter was told of an answer because they asked a question; a room they were in ending is something they can see). **How, and the rule**: `expireLocked` only QUEUES the news on the room (`Room.expired`); `flushExpired` swaps the queue out under `mu` and calls the sink (`Hub.onExpired`, wired by `NewHandler` to `pushInvite`, the same helper every other invite frame uses) with **no lock held**, so a push can never reenter a room or the index. Every method that can settle an invite — `Invite`, `AnswerInvite`, `pendingInviteFor`, `lapse`, `Kick` (which also queues the invites it voids, drained by the same flush) — does `defer r.flushExpired()` BEFORE taking `mu` (so it unwinds after the Unlock), and `Close` calls it after releasing `mu`; **a new method that settles must do the same or the expiry is silent until some other call happens along.** **It is a nudge and nothing depends on it**: `GET /invites` is the truth, nothing here asks `notify.Hub.Listening`, and a frame that lands on no socket loses nothing. `NewHandler` takes the notify fan-out as a func (rooms never imports notify; `cmd/bombers/messaging_wiring_test.go` pins `KindInvite`). **Not the room's in-room `invitation`** (the client prompt a guest ALREADY in the room gets when the host points it at a game) — a different question; do not fuse them. The invite routes sit in the plain auth group beside `POST /rooms`, so — like every route there — an API token passes unscoped. `invites_test.go` covers the opaque 404s, non-member, re-invite, answer-twice, closed/reaped room, the hour, the inviter's frame, nobody listening, and concurrent use, and for expiry: each pending invitee told once on a close, a declined or accepted invitee not told again, the inviter not told, the reaper telling BEFORE it drops the index entry (with both locks probed from inside the push), once-only whichever of a read, the close and the sweep gets there first, and a close/sweep with nobody listening; the tests that pin expiry and the gate were each confirmed to go red when the check was broken, and `member_invites_test.go` does the same for the switch and the widened gate (default off refuses a stranger to the host, on allows it, host-only control, `room:update` and `room:welcome`, accepted admits, declined/expired/another room's/ended-room's admit nobody, switching off evicts nobody and voids nothing, off really means off, and the invite flood cannot forget an accepted invite; and for kick: a kicked stranger cannot reconnect, their invites to other rooms and other members' invites to this room survive, a kicked friend of the host still reconnects by friendship, a pending invite is voided too, both ends are told at once, and a kick of an absent holder of a pending or accepted invite voids it and tells no socket and changes no roster, a kick of someone neither connected nor holding an invite still refuses, and a kick with no invite sends nothing).

- `activities/` -- the **game store** (`handler.go`/`store.go`, tables `activities` + `activity_assets`): the games this server publishes for the client's Play screen. Mirrors the node store deliberately -- an opaque `{manifest, files}` bundle the server never interprets, operator-curated through the console or the admin-gated HTTP path below. The difference is ASSETS: sprites/audio (later models) whose BYTES live in object storage under `activities/<id>/<path>` and whose manifest (path, content type, size) lives in `activity_assets`. `GET /activities` is the catalogue (id/name/version + description/category/players read out of each manifest, plus asset count and total download size -- never the files), `GET /activities/{id}/bundle` returns the bundle spliced in byte-for-byte alongside its asset manifest so an installer needs one round trip, and `GET /activities/{id}/assets/*` streams a single asset **through the server** (never a bucket/presigned URL, same rule as profile media). Asset paths are validated by a narrow positive rule (`ValidAssetPath`: forward slashes, no leading slash, no dot segments, bounded) because a traversal through a published bundle would be the worst kind of bug -- tested. Console: `games` (list), `publish-game <folder>` (reads `manifest.json` + source + `assets/**`, uploads the bytes, records the manifest; republishing REPLACES the asset folder so a removed file stops being served), `unpublish-game <id>` (drops the row -- assets cascade -- and removes the stored bytes). `GET /activities` also surfaces `icon`/`cover` -- asset PATHS read out of the manifest, and only when the game really shipped that file, so a client can show art before installing without chasing 404s.

**Publishing is admin-only over HTTP as well as from the console**, in two steps like the pack store because a game carries binary assets: `POST /activities` (the bundle), `PUT /activities/{id}/assets/*` (one raw-bytes PUT per file), `DELETE /activities/{id}`. Publishing REPLACES -- same id, new bundle, and the asset folder starts over, so art must be re-uploaded after every publish. A `version` is required and is checked here as well as at compile: two players must be on matching builds, and a mismatch produces a desync mid-match rather than an error anyone can read.

`examples/sample-game/` is a working folder to copy and `examples/word-sprint/` is a real game. Connect Four and Chess live in `bombers/games/` -- outside both repos on purpose, like the launcher scripts. The client ships with **zero** games; every one of them installs from this store.

- `packs/` -- the **pack store** (`handler.go`/`store.go`, tables `packs` + `pack_assets`): downloadable bundles for the client. A pack has ONE kind -- a **theme** (colors/fonts/roundness as CSS variables, pure JSON, no assets) or a set of **sounds** (audio clips). Never both, and never a wallpaper: a background belongs to the person running the client and nothing downloaded reaches it. A sound clip's FILENAME means nothing to the server or the client -- the client assigns clips to its sound slots through its own wiring. Same shape as the activity store (bundle + assets, operator-curated); `bundle` is `pack.json` (theme vars live inside it, stored verbatim), and the sound BYTES live in object storage under `packs/<id>/<path>`. Reading, open to any authed user: `GET /packs`, `GET /packs/{id}/bundle`, `GET /packs/{id}/assets/*`. Publishing is **operator-only, two ways into the same operation**: the console (`packs` list, `publish-pack <folder>` -- `pack.json` + `sounds/**`, everything else skipped -- `unpublish-pack <id>`), or the **admin-gated** HTTP path, so an operator can publish from the CLIENT instead of copying a folder onto the server box. That path takes TWO steps where the node store took one, because a pack carries binary assets: `POST /packs` (the body IS `pack.json`; upserts the record and CLEARS the previous asset set, rows and stored bytes both, so a republish replaces rather than accumulates), then one `PUT /packs/{id}/assets/*` per file (raw bytes, `Content-Type` from the header, `packs.UpsertAsset` records the single row), and `DELETE /packs/{id}` to unpublish (idempotent -- `removed: false`, never a 404, matching the node store). Caps: `packs.BundleLimit` 4 MiB (413 `bundle_too_large`), `packs.AssetLimit` 8 MiB (413 `asset_too_large`) -- both shared with the console path so the two can't disagree. `ValidAssetPath` **and** `ValidPackID` are checked before anything touches storage: between them they are the whole of the object key, and a traversal through a published pack would be the worst kind of bug (tested). `examples/sample-theme-pack/` and `examples/sample-sound-pack/` are folders to copy -- one per kind, because a pack is only ever one of them.

- `releases/` — **the app's own updates** (`handler.go`/`store.go`, table `releases`): the desktop client's installers, read by the updater inside a running copy rather than by a person browsing. The fourth store and the smallest — one file and a signature where the others carry a bundle plus assets. `signature` is NOT NULL with no default, because every installed copy verifies a download against the public key compiled into it and a row without one is a release nobody can take. The installer's BYTES live in object storage under `releases/<version>/<file>` and stream **through** the server (never a bucket URL, same rule as media). `GET /releases/latest` emits the **Tauri updater's** manifest shape verbatim — field names and the RFC 3339 `pub_date` are that plugin's contract, not ours — and answers `204` both when the caller is current and when nothing is published, deliberately not distinguishing them. **"Latest" is the most recently PUBLISHED row, not the highest version**, which matches the client's store rule ("different from what's published") and makes republishing an older build the rollback mechanism; a row whose bytes never arrived is skipped, so a half-finished publish keeps serving the previous release instead of offering a download that 404s. The manifest's `url` is derived from the incoming request (honouring `X-Forwarded-Proto`/`-Host`) rather than from configuration, so a LAN server hands out LAN URLs with nothing set. Publishing is **admin-gated HTTP only** — `POST /releases` (metadata + signature; resets the version's size to zero and clears its stored bytes so a republish can't serve the old installer under a new signature), `PUT /releases/{version}/artifact` (raw bytes, 128 MiB cap; the filename comes from step one so the two steps can't disagree), `DELETE /releases/{version}` (idempotent). **A publish PRUNES**: only the newest `KeepReleases` (3) survive, rows and stored bytes both — nothing pointed at the older ones and their installers sat in object storage forever. Three rather than one because `unpublish-release` is the fast rollback and it drops clients onto the newest release STILL published; delete aggressively and you delete the undo. Pruning runs after the new release lands and is never fatal — the publish already succeeded. There is deliberately no `publish-release` console command: the build happens on the operator's Windows desktop and this server is Linux, so a console publish would mean copying the installer onto the box first — the exact step the HTTP path removes. The console keeps `releases` (list, `→` marks the one being offered, `(no file yet)` marks an interrupted publish) and `unpublish-release <version>`.

## What this repo is

The **Bombers Server** — the Go backend half of Bombers. The Tauri/React client lives in a **separate codebase**; this repo is server-only. The API is the product, and the desktop client is just one consumer — never bake client-specific assumptions into endpoints.

Scope is the owner and his friends (tens of users, permanently). Don't over-engineer for scale or federation.

**It runs on Linux.** Developed on a Windows desktop, deployed to an Ubuntu VPS — that's the whole world. Go will cross-compile elsewhere; nothing there is tested and the install path assumes a Unix filesystem. Don't add platform-specific code for Windows or macOS.

**Self-hosting works but isn't a goal** (2026-08-06). The `bombers` CLI, the setup wizard and the server picker all exist and function — the owner uses them to run his own instance — but making that good *for strangers* stopped being something to invest in. Keep the capability, don't build an audience for it. Every server (official or private) is an **isolated island**: no cross-server anything (per `PRODUCT.md`).

## Stack (per `SERVER.md`, settled in code)

- Go 1.25, module `github.com/tabuhana/bombers-server`
- HTTP: `net/http` + `chi` router
- DB: PostgreSQL via `pgx`, hand-written SQL (no `sqlc`). No heavy ORMs.
- Auth: JWT (`golang-jwt/jwt/v5`) — Discord sign-in (no passwords), short access token + long rotating refresh token
- IDs: ULIDs (`oklog/ulid/v2`) — the client's ULID is the join key for `PublishedItem`
- Text: `github.com/rivo/uniseg` — grapheme-cluster segmentation, used by `messaging` to decide that a reaction is exactly one character (`cleanEmoji`); a direct dependency that was already in the module graph
- Real-time: WebSocket via `github.com/coder/websocket` (`rooms/`, `notify/`)
- Migrations: `goose` (`pressly/goose/v3`) — SQL files embedded in the binary (`migrations/embed.go`) and applied through the library
- Config: env vars read by `config.Load` (`.env` loaded first); a self-hosted install layers the `config.json` that `bombers setup` writes to the data dir underneath, filling only what the environment leaves unset

## Layout

Built today: `cmd/bombers/` (wiring) + `internal/{config,store,httpx,logx,types,auth,admin,apitokens,users,discord,settings,friends,profiles,messaging,sync,nodes,nodeshare,noderecords,packs,activities,releases,presence,rooms,notify,imagesize,media,console,setup,embeddedpg,migrate,backup,svc}` (`svc` wraps `kardianos/service` for the P5 background-service mode). Planned per `SERVER.md`: `internal/{sharing,realtime}` (the spec's `events/` is answered by `noderecords/` — an event is a node, and invites are records).

Each `internal/<domain>` owns its own routes, logic, and queries (typical files: `handler.go` HTTP, `service.go` logic, `store.go` pgx queries). Domains stay loosely coupled — don't reach into another domain's internals; depend on `auth` for tokens/middleware and `httpx`/`types`/`store` for shared plumbing. New routes are registered in `cmd/bombers/main.go` (auth-gated ones inside the `RequireAuth` group).

## Mental model that drives everything

- **Local client = working copy. Server = published copy.** The server never edits; it stores what clients have published, and is the substrate for sharing. Don't invert this.
- The server is a **versioned key-value store of published items keyed by ULID, scoped to an account, plus a sharing/permission layer.** Keep this framing when designing sync endpoints.
- **Sync is triggered, not real-time.** Push/pull are explicit operations. The "feels live" layer is a WebSocket nudge → client auto-pulls (except the note the user is actively editing). See `SERVER.md` §Sync.
- **DMs persist forever in Postgres. Rooms persist nothing past expiry.** This asymmetry is intentional.
- **Media ships as slices of one S3 phase — profile media (avatar/banner) and ACTIVITY ASSETS are built; nothing else is.** Photo libraries, note-attachment sync, and room files wait for their own slices (DM pictures are built: they live in the same object store under `messages/<id>/image`) on the same `media/` plumbing. Don't build them piecemeal, and never serve media via direct/presigned bucket URLs — authenticated pass-through only.

## Commands

Standard Go workflow (no `Makefile`):

The binary is a `bombers <command>` CLI. **Running a server is five commands and
never mentions Go or goose:**

```bash
./bombers install    # once, from a fresh clone: builds + puts `bombers` on your PATH
bombers setup        # configure database + media, and migrate. Re-run to change config
bombers start        # run in the background
bombers restart      # stop + start; the command to use after `bombers update`
bombers              # the admin console against it (exiting leaves it running)
bombers stop         # stop it
bombers backup       # everything in one portable file
bombers restore FILE # put it back (REPLACES what's there)
```

`./bombers` in the repo root is a **launcher script**: it compiles the server if
the binary is missing or stale, then execs it — which is why a fresh clone needs
no `go build`. After `install`, it's out of the picture.

- **`install`** — builds from the checkout, installs to `/usr/local/bin` when
  that's writable (a container running as root) else `~/.local/bin` (never sudo;
  prints the PATH line if that directory isn't on it), and records the source +
  binary paths in `<dataDir>/install.json` so `update` works from any directory.
  It configures nothing and touches no database — that's `setup`'s job, kept
  separate so reconfiguring never means reinstalling.
- **`setup`** — the config wizard, then migrates (it now knows where the database
  is). This is the only migration a first install needs.
- **`update`** — pulls the recorded source, rebuilds from it, replaces the
  installed binary, then applies migrations. It PULLS so that "I updated and
  nothing changed" stops being a normal experience, and REFUSES on a dirty tree
  rather than stashing: a binary built from code that exists nowhere else is one
  nobody can reproduce. Not a git checkout, or no git installed → it says so and
  builds what's there.
  It migrates from the checkout's `migrations/` folder, not its own embed: the
  binary running `update` is the old one, so its embedded set is stale
  (`migrate.UpFrom`). It never serves — start the server again afterwards.
- **`start`** backgrounds itself at a terminal (pidfile + `server.log` in the data
  dir; `stop` / `status` / `logs` manage it) and stays in the FOREGROUND when
  stdout isn't a terminal, which is what makes it correct under systemd and in a
  container. `start --foreground` forces the attached path.
- **A bare `bombers`** opens the admin console. A service-manager launch passes no
  arguments either, so that case is detected BEFORE the bare default is applied —
  otherwise systemd would start a console instead of a server.
- `service` (systemd/launchd/Windows Service) remains for start-on-boot and
  restart-on-failure; it is no longer needed just to run in the background.
  **`status` also asks the service manager**: the pidfile only knows about
  `bombers start`, so a service-launched server used to be reported as "not
  running" while it was serving traffic perfectly. The service check is best
  effort — an error or a refusal is a "no", falling back to the pidfile answer,
  because a status command should never fail, only be less certain.
  **`update` REFUSES while the server is running** — it checks both the pidfile
  and the embedded Postgres port, because a service-launched server never
  backgrounds itself and so writes no pidfile. Without that check, `update`'s
  stale-port cleanup reads a LIVE database as a crash leftover and stops it,
  killing the database out from under the running server.
  A service whose **startup fails now EXITS non-zero** instead of asking the
  service manager to stop it: `s.Stop()` under systemd means `systemctl stop`,
  which the service's own unprivileged user may not do — so the call failed, the
  error was discarded, and the process sat there alive serving nothing while
  systemd reported it running. The unit carries `Restart=on-failure` (not
  `always`, so a deliberate stop stays stopped) with a 10s delay, which lets a
  transient cause like a port still held by something shutting down clear itself.
  **`service install` sets the unit's user** (`svc.Config(user)` → `User=`),
  taken from `--user` or `SUDO_USER`, and **REFUSES to install a root-run
  service**. Installing needs root, so without this systemd would run the server
  as root — where the embedded Postgres refuses to start (`initdb: cannot be run
  as root`) and the data dir resolves to root's home instead of the account
  holding it. The failure would be invisible until the first reboot, which is
  why it's a refusal rather than a warning.

- **`backup` / `restore`** — one portable file, and portable is the point: a
  backup that only restores onto an identical setup isn't a backup. The archive
  holds a plain `pg_dump` plus the media as ordinary files, so it goes back into
  whatever the NEW machine runs — one machine's embedded Postgres to another's
  system one, filesystem media to MinIO. `pg_dump`/`psql` come from the PATH and
  must be installed separately (`apt install postgresql-client`) — **the embedded
  distribution ships only the SERVER binaries** (initdb, pg_ctl, postgres), so a
  machine running the built-in database still has no client tools. `doctor`
  checks for pg_dump so that is found before a backup is wanted rather than
  during one. Shelling out rather than serialising rows here is a deliberate
  refusal to be clever, since a hand-rolled dumper that gets one escaping rule
  wrong produces an archive that looks fine and restores wrong. `restore`
  REPLACES everything, makes you type RESTORE, and refuses when stdin isn't a
  terminal unless you pass `--yes`.

Underneath, the plumbing commands still exist: `doctor`, `console`, `version`,
`uninstall`. There is no `migrate` command: `setup` and `update` migrate, and
with embedded Postgres they start the database, migrate, and stop it again,
since nothing is listening between server runs.

```powershell
go build ./...                          # compile everything (binary: bombers)
go run ./cmd/bombers                    # bare = the admin console against a running server
go run ./cmd/bombers start --foreground # run the server attached, with the `bombers>` console
go run ./cmd/bombers start --foreground --headless   # attached, no console; stops on SIGINT/SIGTERM
go run ./cmd/bombers setup              # (re)configure local self-host, then exit (does not serve)
go run ./cmd/bombers doctor             # check the local setup for problems (never serves); exits 1 on any failure
go run ./cmd/bombers console            # open the admin console against a running (headless/service) server — same DB, separate process
go run ./cmd/bombers service install    # register as an OS background service (needs an ADMIN/root shell)
go run ./cmd/bombers service start      # also: stop / restart / status / uninstall the service
go run ./cmd/bombers uninstall          # remove the service + delete the data dir (--yes skips the confirm)
go run ./cmd/bombers version            # print the version
go run ./cmd/bombers help               # list the subcommands
go test ./...                           # run all tests
go test ./internal/auth -run TestRotate   # single package / test
go vet ./...
gofmt -w .
```

A local Postgres + MinIO are available via `docker compose up -d` (Postgres uses `DB_NAME`/`DB_USER`/`DB_PASSWORD`, binds 5432; MinIO uses `S3_ACCESS_KEY`/`S3_SECRET_KEY`, binds 9000 + console 9001 — the server creates the media bucket itself on startup). A `server.exe` may be sitting in the repo root on the Windows dev machine: it's an untracked leftover, not a committed artifact (`.gitignore` excludes `*.exe`) — ignore it and rebuild with `go build`.

### Container hosts (Railway, Fly, plain Docker)

`install` / `setup` / `update` / the admin console are the SELF-HOSTED path and
never run on a platform host: there is no PATH to install into, no wizard to
answer, and no git pull to react to. A platform builds the binary from the repo
and runs it; configuration is env vars.

Two behaviours make `bombers start` the correct start command there with nothing
special configured:

- **It stays in the foreground when stdout isn't a terminal.** Backgrounding is
  for a human shell. In a container, forking away looks exactly like the process
  exiting — the platform would call the deploy dead and restart forever. The same
  check keeps a systemd-launched process in the foreground.
- **`AUTO_MIGRATE=true` applies pending migrations at startup**, so a deploy
  carries its own schema. Opt-in on purpose: on a managed database, schema
  changes shouldn't be a side effect of a restart. Leave it unset and use a
  pre-deploy `bombers update` instead if you'd rather a failed migration block
  the deploy. (The embedded backend always migrates itself and ignores this.)

`PORT` is read from the environment (platforms inject it), `/health` is the
health-check path, and SIGTERM triggers the graceful shutdown a redeploy needs.

### Migrations (goose)

Migrations live in `migrations/` at the repo root, written as `-- +goose Up` / `-- +goose Down` SQL files.

**The easy path — `bombers update`.** The binary embeds the migrations and applies them through the goose LIBRARY (the same path embedded Postgres uses at startup), so updating any database — external/dockerised included — needs no goose CLI, no exported `DATABASE_URL`, and no `-dir` flag. It reads `.env` and the saved config exactly like the server, applies what's pending, and exits without serving; an unreachable database reports one clean line instead of pgx's address dump. There is no separate `migrate` COMMAND — migrating is plumbing, so `update` (after a pull) and `setup` (first install) are the two commands that do it; startup itself migrates only for embedded Postgres or with `AUTO_MIGRATE=true`. `update` refuses while the server is running, and it reads the migrations from the checkout it just rebuilt rather than its own embed, because the binary running it is the OLD one (`migrate.UpFrom`). So: `bombers stop`, `bombers update`, `bombers start`.

The goose CLI remains available for the things a library call can't do (`down`, `status`, `create`):

```powershell
go install github.com/pressly/goose/v3/cmd/goose@latest
```

Run from the repo root (assumes `DATABASE_URL` is set, e.g. via `.env`):

```powershell
goose -dir migrations postgres $env:DATABASE_URL up        # apply all pending
goose -dir migrations postgres $env:DATABASE_URL status    # show applied/pending
goose -dir migrations postgres $env:DATABASE_URL down      # roll back last
goose -dir migrations postgres $env:DATABASE_URL create <name> sql   # new migration
```

New migration filenames are timestamped (`YYYYMMDDHHMMSS_<name>.sql`).

## Hard constraints (refuse these — see `PRODUCT.md` and `SERVER.md`)

- No federation, cross-server, or multi-server logic.
- No public discovery / username search endpoints. Friend codes only.
- No media beyond the built profile avatar/banner slice and the one picture an image message carries (no photo libraries, no multi-attachment messages, no room files yet), and no direct/presigned bucket URLs — media serves through the server only.
- No OS push infrastructure — in-app indicators only.
- No persisting rooms past expiry.
- No baking Tauri-client assumptions into the API.
- No making the server authoritative over the working copy.
